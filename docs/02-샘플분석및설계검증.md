# 실제 샘플 분석 및 설계 검증

작성일 2026-09-13. `test/fixtures-local/` 의 실제 업무 파일 5개를 셀·좌표 단위로 직접 열어 분석하고,
`docs/01-설계안.md` 의 가정을 검증한 결과다.

> **2026-09-13 갱신** — 이 분석을 본 사용자가 업무 규칙 12가지를 확정했다(`01-설계안.md` **14장**).
> 아래 10장 B 항목 중 B1·B2·B3 은 그 결정으로 **확정**됐고, **7장의 유효 품목 규칙은 14장 9·10번으로 바뀌었다**
> (행을 다섯 종류로 나누고, 할인은 `N종` 에서 빼되 총액에는 넣으며, 금액 0원 행은 전부에서 빼되 참고로 보여 준다).
> **6장의 문구 예외와 3장의 파일명 결론도 14장 11·1번으로 정리됐다.** 설계안은 개정을 마쳤다.
> **남은 C 질문은 C5·C6 둘뿐이고 P1 착수를 막지 않는다.** 2~9장의 **분석 사실 자체는 그대로**다.

분석에 쓴 스크립트는 세션 스크래치에만 있다. P0 에서 Rust 시험으로 다시 만든다.

**용어 주의**: 이 문서에서 "관리명" 이라고 쓴 곳은 개정 설계안의 **거래처 관리명**(`vendor_unit.mgmt_name`)이고,
정산자료 `부서명` 열의 이름은 **정산 별칭**(`settlement_alias.alias`)이다. 둘은 다른 개념이다(설계안 2장).

### 2-4. RawTable 방식으로 처리 가능한가 — 가능하다. 단 두 가지를 고쳐야 한다

세 견적서 모두 "격자로 만든 뒤 머리글 낱말로 열 역할을 정한다" 는 방식이 통한다. 다만 실측에서 두 군데가 깨졌다.

**(가) 이미지의 열 경계는 머리글 위치로 나누면 안 된다.**
머리글 중심 최근접으로 배정하니 왼쪽 정렬된 짧은 품명(`10급Yap!`, `암산교재`)이 `순번` 열로 끌려갔고,
머리글 사이 중간점으로 경계를 만드니 이번엔 품명 전체가 `순번` 으로 갔다. `품 명/규 격` 머리글이
넓은 열의 가운데에 있는데 자료는 왼쪽에 붙어 있기 때문이다.

**통한 방법**: 열 경계를 **본문 행의 x 구간 겹침으로 군집화**해 만들고, 그 군집에 **가장 가까운 머리글 이름을 나중에 붙인다.**
실측 군집 `(226,243) (307,624) (1045,1074) (1237,1254) (1324,1434) (1651,1764)` → 6열이 정확히 분리됐고
이름도 `순번·품명/규격·단위·수량·단가·공급가액` 로 바르게 붙었다. 표가 완전히 복원됐고 4행 모두 검증을 통과했다.

**(나) 표가 여러 개일 때 "품목 행이 가장 많은 표" 로는 못 고른다.**
로봇과학 견적서의 `견적서`·`납품서` 표는 행 수도 내용도 같다. **표 제목 글자(`견적서`/`견 적 서`)를 보고 골라야 한다.**
없으면 문서에서 먼저 나오는 표를 쓰고 경고한다.

## 3. 부서 / 관리명 자동 매칭 — 실제 파일명으로 검증

| 파일명 | 정규화 | 등록 관리명과 비교 | 결과 |
|---|---|---|---|
| `바둑 견적서.xlsx` | `바둑견적서` | `바둑` 포함 | **자동 매칭** |
| `주산암산 견적서.jpg` | `주산암산견적서` | `주산암산` 포함 | **자동 매칭** |
| `로봇과학 견적서.hwp` | `로봇과학견적서` | `로봇과학1`·`로봇과학2` 어느 쪽도 정확히 포함하지 않음. 표시 부서명 `로봇과학` 에만 걸림 | **사용자 확인 필요** (거래처 후보 2개) |

**이 샘플 파일명에는 거래처 관리명 뒤 숫자가 없었다.** 샘플을 만들 때 파일명 규칙을 적용하지 않았기 때문이다(14장 8번).

**확정된 운영 규칙**(14장 1번)은 **"파일명에 최소한 부서명을 반드시 넣고, 거래처가 여러 개인 부서는 거래처 관리명까지 넣는다"** 이다.
**형식은 강제하지 않는다** — `주산암산부 견적서.jpg` · `주산암산 견적서.jpg` · `주산암산 견적서류.jpg` ·
`주산암산 9월 견적서.jpg` 가 모두 똑같이 매칭된다. `부`·`견적서`·`견적서류`·월 표시는 매칭에 영향이 없다.

그래서 위 표의 결과는 규칙 아래에서도 그대로다. 바둑·주산암산은 부서에 거래처가 하나뿐이라 **자동 매칭**이고,
`로봇과학 견적서.hwp` 는 거래처가 둘인 부서에 부서명만 있으므로 **추측하지 않고**
"로봇과학 부서는 거래처가 여러 개입니다" 라고 알린 뒤 사용자가 고른다.

숫자 제거는 정규식으로 하지 않는다. `vendor_unit.department_id` → `department.phrase_name` 으로만 품의 표기명을 얻는다.
그리고 **파일명 매칭 대상은 거래처 관리명과 품의 부서명뿐이다. 정산 별칭은 쓰지 않는다** —
쓰면 `토탈공예미니어처1 견적서.xlsx` 가 있지도 않은 거래처로 붙는다(4장 참고).

| 머리글 1행 | `부서명` · `수익자(1,2,4,5,6학년)` · `3학년 초과금` · `3학년 지원금` · `자유수강권` · `합계` |
| 자료 | 2~21행 (20행) |
| 합계 행 | 22행, A22 = `합계` |
| 자료형 | 금액 전부 **숫자 셀**(`t` 속성 없음), 표시 형식 `#,##0`. **수식 없음**(값으로 저장) |
| 틀 고정 | `A2` |
| 검산 | 20행 모두 `수익자+초과금+지원금+자유수강권 = 합계` **성립**. 열별 합도 22행 합계와 **일치** |

### 4-2. 행 키는 관리명인가 부서명인가 — **둘 다 아니다. "강좌(반)" 단위다**

정산자료 20행에는 숫자가 붙은 이름이 실제로 있다.

```
토탈공예미니어처    수익자 115,000  지원금 115,000
토탈공예미니어처1   수익자 460,000
토탈공예미니어처2   수익자 115,000
목요키즈쿠킹       수익자 805,000
화요키즈쿠킹       수익자 1,344,000
```

그런데 사람이 실제로 만든 품의서에서 이 다섯 행은 **두 줄로 합쳐졌다.**

```
토탈공예미니어처부 보관함 세트 외 2종 | 식 | 1 | 690,000   ← 115,000+460,000+115,000
키즈쿠킹부 초코칩쿠키 외 10종        | 식 | 1 | 2,191,000  ← 목요+화요
```

**즉 정산자료의 `1`·`2` 접미사는 거래처 구분이 아니다.** 같은 부서의 다른 반/요일이고, 품의에서는 도로 합쳐진다.
요구사항 3장의 관리명 `로봇과학1`·`로봇과학2`(거래처 구분)와는 **다른 개념이며, 이름 모양이 같아서 위험하다.**

반대 방향도 실제로 있었다. 정산 한 줄이 품의 두 줄로 **쪼개졌다.**

```
정산  로봇과학  수익자 810,000  →  품의  로봇과학부 프로보테크닉 교구 외 1종  720,000
                                    로봇과학부 익스트림에디션 키트 외 1종  90,000
정산  체스      수익자 268,000  →  품의  체스부 매직체스스쿨 1종            196,000
                                    체스부 체스는내친구 1종               72,000
```

### 4-3. 결론: 거래처별 배분은 현재 샘플로 계산할 수 없다

로봇과학으로 확인해 보면:

| | 견적 총액 | 수익자 | 초과금+지원금 |
|---|---|---|---|
| 로봇과학1 (받은 견적서) | 900,000 | 720,000 (실제 품의서) | 180,000 |
| 로봇과학2 (견적서 없음) | 360,000 (추정) | 90,000 (실제 품의서) | 270,000 |
| **정산자료 로봇과학 한 줄** | **1,260,000** | **810,000** | **450,000** |

합은 맞지만(180,000+270,000 = 450,000 = 6,200+443,800), **어느 거래처가 초과금을 얼마 썼는지는 정산자료 어디에도 없다.**
자동 비율 배분은 회계자료에 추정값을 넣는 일이므로 **구현하지 않는다**(설계 2-1 (C) 유지).

**확정된 구조** (설계안 14장 4·5·6번):

- 여러 정산 행 → 한 품의 부서: **자동 합산.** 어떤 정산 별칭이 어느 부서로 합쳐지는지는 부서 설정에서 사람이 등록한다.
- 한 품의 부서 → 여러 거래처: **사용자가 재원 4칸을 각각 입력.** 총액만 입력하는 방식이 아니다. 자동 배분은 하지 않는다.
- 검증은 두 방향이다.
  **세로** — 거래처별 같은 재원의 합 == 정산자료의 그 재원 금액(4개 각각).
  **가로** — 한 거래처의 재원 4개 합 == 그 거래처 견적서 총액.
  둘 다 맞아야 정상이고, 어긋나면 빨강으로 막되 프로그램이 금액을 채우거나 고치지 않는다.

로봇과학 배분 화면이 실제로 이런 모습이 된다.

```
                수익자     초과금    지원금    자유수강권       합계      견적 총액   가로
로봇과학1       [입력]    [입력]    [입력]     [입력]        자동      900,000    ✔/✘
로봇과학2       [입력]    [입력]    [입력]     [입력]        자동      360,000    ✔/✘
──────────────────────────────────────────────────────────────────────────────
정산자료 합계   810,000    6,200   443,800        0       1,260,000
세로              ✔/✘      ✔/✘      ✔/✘       ✔/✘
```

## 7. 유효 품목 규칙 — 샘플로는 판단 불가

세 견적서에서 찾아본 결과:

| 찾은 것 | 바둑 | 로봇과학 | 주산암산 |
|---|---|---|---|
| 배송비·택배비 | 없음 | 없음 | 없음 |
| 할인 | 없음 | 없음 | 없음 |
| 부가세 행 | 없음 | 없음 | 없음 |
| 소계 행 | 없음 | 없음 | 없음 |
| 합계 행 | 30행 `계` | 34행 `계` | **없음** |
| 금액 0원 행 | 13~29행 (수식 0) | 12~33행 (빈칸) | 없음 |
| 수량 0 행 | 위와 같음 | 위와 같음 | 없음 |
| 사은품 | 없음 | 없음 | 없음 |

**배송비·할인·사은품 행은 세 샘플 어디에도 없다.** 그래서 이 표만으로는 판단할 수 없었고 사용자 결정으로 넘겼다.

> **2026-09-13 확정 (설계안 14장 9번)**
> - **배송비·택배비**: 현재 업무 견적서에 없다 → **지금은 별도 규칙을 만들지 않는다.** 실제로 나타나면 그때 추가한다.
> - **할인**: 있으면 **반드시 읽는다.** **`N종` 에서 제외**하고 대표품목 후보도 아니지만 **견적 총액에는 반영**한다.
>   금액은 **원문 그대로** 쓰고 프로그램이 부호를 바꾸거나 할인액을 계산하지 않는다.
>   표기가 양식마다 다르므로(`할인` · `할인금액` · `DC -30,000`) 부호가 총액에 어떻게 반영되는지는 **검산으로 판별**한다.
> - **행 분류를 다섯 종류로 바꿨다**: `일반 품목` · `할인/금액 조정` · `금액 0원 행` · `합계/소계` · `빈 행`.
> - **사은품·금액 0원 행** (14장 10번): 금액이 0원이면 품의 금액에 영향이 없으므로
>   **`N종`·대표품목·견적 총액에서 모두 제외**하되, **원문에 있으므로 지우지 않고 참고용으로 보여 준다.**
>   판별 기준은 `사은품` 이라는 낱말이 아니라 **금액이 0인지**다. 그래서 행 종류는 **다섯**이 됐다.

아래 규칙은 **할인 행이 없는 경우에 한해** 여전히 맞다. `이름이 있고 금액이 0보다 큰 행만 품목으로 센다` 로
**세 건 모두 정확한 종수**가 나왔다(1종 · 2종 · 4종, 실제 품의서와 일치). 빈 행·합계 행 제외도 충분했다.
**다만 이 규칙만으로는 할인 행을 가를 수 없다** — 할인도 이름이 있고 금액이 0이 아니기 때문이다.
그래서 설계는 "금액이 0보다 큰가" 가 아니라 **"행 종류가 무엇인가"** 를 먼저 정하는 쪽으로 바뀌었다(설계안 6-2).

## 8. 금액 검증 — 견적 총액 = 네 재원의 합

| 견적서 | 견적 합계금액 | 수익자 | 초과금 | 지원금 | 자유수강권 | 재원 합 | 판정 |
|---|---|---|---|---|---|---|---|
| 바둑 | **444,000** | 372,000 | 12,000 | 60,000 | 0 | **444,000** | **일치** |
| 주산암산 | **68,000** | 40,000 | 0 | 18,000 | 10,000 | **68,000** | **일치** |
| 로봇과학(거래처 1곳분) | 900,000 | 810,000 | 6,200 | 443,800 | 0 | 1,260,000 | **불일치** — 정산 행은 부서 전체이고 두 번째 견적서가 없다 |

**거래처가 하나인 부서는 `견적 합계금액 = 수익자+초과금+지원금+자유수강권` 이 정확히 성립한다.**

### 8-1. 비교 기준은 "합계금액(공급가액+세액)"

세 견적서 모두 **세액이 0**이다(도서 면세 / 단가에 부가세 포함). 그래서 공급가액 = 합계금액이고 어느 쪽으로 비교해도 맞는다.
다만 세 양식 모두 `합계금액(공급가액+세액)` 이라는 칸을 따로 두고 있으므로, **그 값(총액)을 정산과 비교하는 기본값**으로 삼는 것이 맞다.
세액이 0이 아닌 견적서 샘플이 없어 확증은 아니다 → 견적서마다 비교 기준을 바꿀 수 있게 두는 설계(2-2)는 그대로 둔다.

### 8-2. 합계 표기값을 못 읽는 경우가 실제로 있다

주산암산 이미지의 `₩68,000` 은 OCR 이 `鬧8,000` 으로 읽었다. 품목 합 68,000 은 정확했고 네 행 모두 `수량×단가=금액` 을 통과했다.
**"표기 합계를 못 읽으면 품목 합으로 대체하고 경고" 는 실제로 필요한 경로**다(설계 6-1 5번 유지).

## 10. `docs/01-설계안.md` 검토 결과

### A. 그대로 유지할 설계

- **3장 전체 구조** — 모든 형식을 `RawTable` 로 정규화한 뒤 공통 표 해석기 하나가 품목을 뽑는 구조. 세 형식 실측으로 타당성 확인.
- **HWP → 한글 COM → HWPX → 순수 Rust 파서** 경로. 실제로 변환·파싱에 성공했다(5장).
- **부서 / 관리 단위 분리**, 숫자 제거를 정규식이 아니라 `management_unit → department` 조회로 하는 원칙. 4장에서 이 원칙이 더 중요해졌다.
- **품의 표기명(`phrase_name`)을 부서마다 저장**. 키즈쿠킹·토탈공예미니어처 사례가 필요성을 입증했다.
- **문구 자동 생성 규칙**(`1종` / `외 N종`, 대표품목 = 첫 유효 품목, 사용자 수정 가능). 3건 중 2건 완전 일치, 1건은 사용자가 줄인 경우.
- **금액 불일치 시 자동 보정 금지·경고**. 실제 자료에 24,000원 차이가 있었다.
- **2-6 불일치 차단 + 확인 사유 입력** 제안, **2-7 0원 재원 파일 미생성** 제안, **2-9 월별 작업 보존** 제안.
- **8-1 파일명 매칭 4단계**(부서까지 좁히고 거래처는 사용자 선택). 로봇과학 파일명이 정확히 이 경로를 탄다.
- **9장 검증식**(수량×단가, 품목합, 견적↔정산), **10장 생성 후 다시 읽어 검증**.
- **11장 단계 구성**(P0 탐침 → P1 XLSX/HWP → P2 PDF → P3 OCR → P4 배포).

개정 설계안에 **반영 완료**다. 아래는 무엇이 왜 바뀌었는지의 기록이다.

**샘플 보존**: `test/fixtures-local/` 원본 5개는 고치지 않는다. 변환 산출물·시험 결과는 `test/out/`(비커밋)에 둔다.

## 12. 이 문서의 위치

내 제안 중 아직 승인되지 않은 것(불일치 시 생성 차단 방식, 0원 재원 파일, 월별 작업 보존)은
14장이 아니라 **13-2 "승인 대기 중인 제안"** 에 따로 두었다.
