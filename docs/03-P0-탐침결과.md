## P0-1 에듀파인 XLSX 재현

**무엇을 시험했나** — `rust_xlsxwriter` 로 만든 품의 파일이 실제 업로드에 쓴 샘플과 셀 단위로 같은가.
**샘플** — `9월 교재 재료 품의서(1).xlsx` (읽기만). **산출** — `test/out/p0-1-생성.xlsx`.

**실제 결과** — 셀 80개(머리글 4 + 자료 19행 × 4열)가 **값 · 자료형 · 표시형식 · 글꼴 이름/크기/굵기/색 ·
채우기 · 가로세로 정렬 · 줄바꿈 · 네 방향 테두리(선 모양과 색)** 까지 전부 일치했다.
시트 `품목내역` 하나, 범위 `A1:D20`, 병합·숨김·수식·합계 행 없음도 양쪽 같다.
`calamine` 으로 다시 읽어 19행 합계 7,886,900 을 확인했고, 제3의 판독기(openpyxl)로도 교차 확인했다.

**통과/실패** — **통과.**

**발견한 문제 넷** (모두 해결했거나 기록함)

1. **자기닫음 태그를 놓치면 스타일 번호가 통째로 밀린다.** `<xf .../>` 는 `Event::Empty` 로 오고 `End` 가 없다.
   Start 만 보고 End 에서 담으면 자기닫음 항목이 빠져 이후 모든 셀의 서식이 어긋난다.
   → 판독기에서 Empty 를 그 자리에서 담도록 고쳤다. **P1 의 XLSX 파서에도 같은 함정이 있다.**
2. **샘플의 실제 모습을 처음에 잘못 알았다.** 머리글은 연한 파랑이 아니라
   **검정 바탕 + 흰 굵은 글씨 + 빨강 가는 테두리**이고, **B1~D1 은 왼쪽 선이 없다**(A1 만 있다).
   `has_border` 를 참/거짓 하나로만 보던 첫 판독기는 이걸 놓쳤다 → 네 방향을 따로 보도록 고쳤다.
3. **색은 `rgb`·`indexed`·`theme`·`auto` 로 제각각 적힌다.** 서로 다른 생성기가 만든 파일은
   XML 이 같을 수 없으므로 **RGB 로 정규화해서 뜻을 비교**해야 한다.
   샘플은 흰색을 `indexed="9"`, 우리는 `rgb="FFFFFFFF"` 로 적지만 같은 색이다.
   또 본문 글자색은 샘플이 **아무것도 안 적고**(자동) rust_xlsxwriter 는 `theme="1"`(dk1)을 적는데, 둘은 같은 뜻이다.
4. **열 너비 44.5 와 12.25 는 `rust_xlsxwriter` 로 만들 수 없다.** 이 라이브러리는 문자너비를 픽셀로 바꿨다가
   되돌리므로 저장값이 픽셀 단위(약 0.14 문자)로 양자화된다. 80~330픽셀을 **전수 확인**했고 두 값 모두 도달 불가였다
   (`p0_1b_colwidth`). 가장 가까운 값(311픽셀 → 44.426, 86픽셀 → 12.285)을 쓴다. **차이는 0.04~0.07 문자로 눈에 안 보인다.**

**설계 수정 필요 여부** — 설계안 10장의 사양은 그대로 맞다. 다만 **"서식까지 똑같이"의 뜻을
"XML 이 같다" 가 아니라 "화면에 보이는 값과 서식이 같다"로** 적어 두어야 한다. 열 너비는 예외로 기록한다.
이 판독기(`probe/src/xlsx_spec.rs`)는 P1 의 **"생성 후 다시 읽어 검증"** 단계에 그대로 쓸 수 있다.

> **2026-09-13 확증 완료.** 사용자가 이 사양으로 만든 파일을 **실제 에듀파인에 올려 정상 업로드되는 것을 확인했다.**
> P0-1 에 남아 있던 "사람만 할 수 있는 마지막 확인" 은 끝났고, 이 사양은 추정이 아니라 **실제 업로드로 검증된 규격**이다.

## P0-2 XLSX 견적서 파싱

**무엇을 시험했나** — 거래처 양식에서 머리글을 **자동으로** 찾고 품목만 뽑아 내는가.
셀 위치를 하드코딩하지 않는다. **샘플** — `바둑 견적서.xlsx` (읽기만).

**실제 결과**

```
시트 크기 29행 x 9열, 사용 영역 시작 = 엑셀 2행 2열
머리글 = 엑셀 11행 (자동으로 찾음)
열 역할 = name(0) spec(1) qty(2) unit_price(3) amount(6) note(8)
품목 1건: 바둑교재(상상바둑) / 권 / 37 / 12,000 / 444,000
빈 행 17개와 합계 행은 품목에 섞이지 않음
표기 합계금액 444,000 · 합계 행 값 444,000 · 품목 합 444,000
검증 37 x 12,000 = 444,000  OK
자동 문구: 바둑부 바둑교재(상상바둑) 1종
정산 재원 합계 372,000+12,000+60,000+0 = 444,000  일치
```

**통과/실패** — **통과.** 문구도 품목명 원문 그대로 나온다(14장 2번).

**발견한 문제 둘**

1. **`calamine` 의 `Range` 는 A1 이 아니라 "실제로 쓴 영역"에서 시작한다.** 이 샘플은 엑셀 2행 2열부터다.
   화면에 **원본 셀 주소를 보여주려면 `range.start()` 를 더해 절대 좌표로 바꿔야** 한다.
   그냥 쓰면 "11행" 이 "9행" 으로 표시된다.
2. **병합된 열은 머리글 칸과 값 칸의 차례가 다르다.** 이 양식은 단가가 `E:G`, 공급가액이 `H:I` 로 병합돼 있다.
   → 역할별로 **머리글 차례부터 다음 역할 머리글 차례 직전까지**를 그 열의 범위로 잡고,
   그 안에서 값이 있는 첫 칸을 쓴다. 이 방식으로 병합 53개짜리 양식이 정확히 읽혔다.

**설계 수정 필요 여부** — 설계안 6-1 의 절차 그대로 통했다. 위 두 가지를 6-1 에 주의로 적어 둔다.

## P0-4 HWP → HWPX 변환 (한글 COM)

**무엇을 시험했나** — Rust 의 `windows` 크레이트 IDispatch 로 한글 2018 을 몰아 HWPX 로 저장할 수 있는가.
**샘플** — `로봇과학 견적서.hwp` (읽기만). **산출** — `test/out/p0-4-로봇과학.hwpx`.

**실제 결과**

```
RegisterModule → false   (보안 모듈 미등록. %TEMP% 경유라 진행에 지장 없음)
창 감추기 성공
Open → true
SaveAs("...", "HWPX", "") → true
결과 64,227 바이트, 3.1초
HWPX 안: mimetype · version.xml · Contents/header.xml · Contents/section0.xml ·
         BinData/image1.bmp · Preview/* · META-INF/* · settings.xml
mimetype = application/hwp+zip
변환 뒤 한글 프로세스 잔류 없음, 원본 HWP 크기 그대로
```

**통과/실패** — **통과.** PowerShell 로 얻은 64,227 바이트와 **정확히 같은 크기**가 Rust 에서도 나왔다.

**발견한 문제 하나**

- **`windows` 크레이트에 `Win32_System_Com_StructuredStorage` 기능이 필요하다.**
  `BSTR::try_from(&VARIANT)` 와 `VARIANT: Display` 구현이 이 기능에 걸려 있어, 빠뜨리면
  "그런 트레잇이 없다" 는 엉뚱한 오류가 난다. 이름만 봐서는 VARIANT 와 무관해 보여 찾기 어렵다.

**설계 수정 필요 여부** — 없다. 문서 통합 도구의 COM 헬퍼(`com.rs`)를 **그대로** 가져와 썼고 잘 돈다.
VT_BOOL 1 을 참으로 읽는 처리(`as_bool`)가 실제로 필요했다 — `Open`·`SaveAs` 가 1 을 돌려준다.

## P0-5 HWPX 표 파싱

**무엇을 시험했나** — 견적서 표를 **골라**(납품서가 아니라) 병합을 반영해 품목을 뽑는가.
**샘플** — P0-4 산출물.

**실제 결과**

```
표 2개
  표0 제목 "No.   견  적  서"   35행
  표1 제목 "No.   납  품  서"   35행
고른 표: 0 (제목이 견적서)
격자 35행 x 17열  (cellAddr 로 복원)
머리글 행 9, 낱말 7개 일치: 품명 규격 수량 단가 공급가액 세액 비고
열 역할: name(0) spec(3) qty(5) unit_price(7) amount(11) tax(13) note(16)
품목 2건
  프로보테크닉 교구 / set / 10 / 76,500 / 765,000   OK
  프로보테크닉 교재 / set / 10 / 13,500 / 135,000   OK
품목 합 900,000 · 합계 행 900,000 · 합계금액 칸 900,000
자동 문구: 로봇과학부 프로보테크닉 교구 외 1종
```

**통과/실패** — **통과.** 사람이 실제로 쓴 문구와 글자까지 같다.

**발견한 문제 둘**

1. **괄호를 회계식 음수로 보는 규칙에 함정이 있다.** 이 견적서는 합계를 `(￦ 900,000 )` 로 적는데,
   "괄호로 감싸면 음수" 규칙이 이걸 **-900,000 으로 읽었다.** 실제로 시험이 여기서 한 번 실패했다.
   → **괄호 안이 숫자·쉼표·마침표·공백뿐일 때만** 음수로 본다. `(30,000)` 은 음수, `(￦ 900,000 )` 는 양수.
   P0-2 에도 같은 규칙을 넣고 시험을 따로 만들었다(`p0_2_paren_is_not_always_negative`).
2. **두 표는 행 수도 내용도 똑같다.** 02 문서에서 예상한 대로 "품목 행이 가장 많은 표" 로는 못 고른다.
   **제목 글자로 골라야** 한다는 것이 실물로 확인됐다.

**설계 수정 필요 여부** — 설계안 6-1 5번의 숫자 정규화 설명에 **괄호 예외**를 적어야 한다(아래 "설계 반영" 참고).
6-1 1번(제목으로 표 고르기)과 `cellAddr` 격자 복원은 그대로 맞다.

## P0-6 이미지 견적서 OCR

**무엇을 시험했나** — Rust 에서 Windows 내장 OCR 을 한국어로 부르고, 3배 확대 후
**본문 행의 x 구간 군집**으로 열을 만들어 표를 복원하는가. **샘플** — `주산암산 견적서.jpg` (읽기만).

**실제 결과**

```
설치된 OCR 언어: ["ko"]
배율 x1: 블록 46개, 품목명 0/4 정확      ← 원본 크기로는 한글이 다 깨진다
배율 x3: 블록 59개, 품목명 4/4 정확
기울기 0도
행 19개로 묶임 (허용치 = 중앙 글자높이 x 0.6 = 21.0)
머리글 행 12, 낱말 6개 일치: 순번 · 품 명/규 격 · 단위 · 수량 · 단가 · 공급가액
  (세액은 "OH", 비고는 "비"/"고" 로 깨짐 — 그래도 6개면 충분)
열 군집 6개: (227,244) (308,625) (1046,1075) (1238,1255) (1325,1435) (1652,1765)
열 이름 붙이기: 순번 · 품명/규격 · 단위 · 수량 · 단가 · 공급가액
복원된 품목 4건 — 네 행 모두 수량 x 단가 = 금액 통과
  방과후 기초Yap! 상   3 x 10,000 = 30,000
  방과후 기초Yap! 하   1 x 10,000 = 10,000
  10급Yap!           2 x 10,000 = 20,000
  암산교재            1 x  8,000 =  8,000
품목 합 68,000 = 정산자료 주산암산 재원 합계(40,000+0+18,000+10,000)
표기 합계금액 읽기: 실패(None) → 품목 합으로 대체
자동 문구: 주산암산부 방과후 기초Yap! 상 외 3종
```

**통과/실패** — **통과.** 사람이 실제로 쓴 문구와 글자까지 같다.

**발견한 문제 둘**

1. **3배 확대는 선택이 아니라 필수다.** 원본 크기에서는 품목명이 **0/4** 였다. 시험이 이 사실을
   단언으로 못 박아 두었다(원본 크기에서 다 맞으면 오히려 시험이 실패한다 — 규칙을 다시 보라는 뜻).
2. **`₩` 가 붙은 합계는 3배에서도 못 읽는다.** 원본 `₩68,000` 을 아예 못 찾거나 `鬧8,000` 으로 읽는다.
   **품목 합으로 대체하는 경로가 정식 경로**라는 설계 판단이 실물로 뒷받침됐다.
   그리고 품목 합 68,000 은 정산자료와 정확히 맞았으므로, 이 대체가 안전하다는 근거도 함께 얻었다.

**설계 수정 필요 여부** — 설계안 7장(3배 확대·신뢰도 계산)과 6-3(x 군집으로 열 만들기)이 그대로 맞다.
다만 **열 이름을 붙일 때는 "군집 중심에 가장 가까운 머리글"** 이라는 점을 6-3 에 명시해 두는 것이 좋다
(머리글 위치로 열을 나누는 것과는 반대 방향이다).
