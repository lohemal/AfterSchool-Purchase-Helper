# 한글 입력(IME) 조합 깨짐 — 원인과 수정

2026-09-13. 사용자 P1 실사용 시험에서 나온 버그 하나를 고친 기록.
설계 반영은 `01-설계안.md` 5-0장.

---

## 1. 무슨 일이 있었나

추출 결과 확인 화면에서 품목 표시명을 직접 치면 한글이 완성되지 않고 자모가 쌓였다.
사용자의 시험 자료(`work_quote_item`)에 그대로 남아 있었다.

| 치려던 글자 | 실제로 저장된 값 |
|---|---|
| `방과후 기초Yap! 상` | `ㅂ바방ㄱ고과괗후훅기깇초초Yap!ㅅ사살살` |
| `방과후 기초Yap! 하` | `ㅂ바방ㄱ고과ㅎ후ㄱ기깇초초Yap!ㅎ하하` |
| `10급Yap!` | `10ㄱ그급급Yap!` |
| `암산교재` | `ㅇ아암ㅅ사산ㄱ교굦재재` |

**조합 중간 단계가 지워지지 않고 하나씩 덧붙었다.** 숫자 칸은 멀쩡했다.

---

## 2. 정확한 원인

`ReviewStep.tsx` 의 품목 표시명·규격 칸이 이렇게 돼 있었다.

```tsx
<input
  value={it.displayName}                                   // 서버에서 온 값
  onChange={(e) => saveItem(it, { displayName: e.target.value })}
/>

async function saveItem(...) {
  await ipc.updateItem(...)   // IPC → SQLite
  await refresh()             // 목록을 통째로 다시 읽어 setQuotes(...)
}
```

**글자를 한 번 칠 때마다 서버를 다녀와 `value` 를 다시 써 넣었다.**

한국어 IME 는 `ㅂ → 바 → 방` 처럼 **조합 중인 임시 글자**를 입력칸에 올려 두고,
브라우저는 그동안 자기 조합 버퍼를 들고 있다. 그런데 저장·되읽기가 **비동기**라
돌아온 값이 **조합 도중에** 칸에 꽂혔다. 그러면

1. 칸의 값이 바깥에서 바뀌고 → 브라우저의 조합 버퍼와 어긋나고
2. IME 는 조합을 새로 시작하고 → 앞의 중간 글자가 확정된 채 남는다

그래서 중간 단계가 차곡차곡 쌓였다.

**숫자 칸이 멀쩡했던 이유도 같다.** 수량·단가·금액은 `defaultValue` + `onBlur` 였다 —
치는 동안 값을 덮어쓰지 않았다.

> 사용자가 준 조사 항목으로 정리하면 원인은 **4번(onChange 마다 백엔드 저장·외부 상태 재동기화)** 과
> **5번(재렌더링으로 composition 도중 value 재주입)** 이다.
> 6번(key 변경으로 DOM 재생성)은 아니었고, 7번(composition 처리)이 **없던 것**이 문제를 키웠다.

## 3. 어떻게 고쳤나

### 3-1. 규칙을 순수 함수로 (`src/lib/imeText.ts`)

상태 기계 하나로 규칙을 못 박았다. 화면 없이 시험할 수 있다.

| 사건 | 하는 일 |
|---|---|
| `change` | **화면 값만** 바꾼다. 저장하지 않는다 |
| `compositionStart` / `compositionEnd` | 조합 중임을 표시 / 완성된 글자를 받는다 |
| `external`(부모가 준 새 값) | **조합 중이면 무시.** 초점이 있고 고친 상태여도 무시 |
| `blur` · `commitRequest`(Enter) | 조합이 끝난 뒤 **한 번만** 확정 |

핵심은 `external` 의 첫 줄이다 — **조합 중에는 바깥 값을 절대 받아들이지 않는다.**

### 3-2. 공통 컴포넌트 (`src/components/TextField.tsx`)

위 상태 기계를 쓰는 입력칸. 사용자가 글자를 칠 수 있는 칸은 **예외 없이** 이것을 쓴다.

- `value` — 바깥 값 (받아들일지는 상태 기계가 정한다)
- `onCommit(v)` — **확정될 때만** 불린다
- `onDraftChange(v)` — 치는 동안의 값 (단추를 켜고 끄는 용도. 없어도 된다)

글자를 다듬지 않는다. 앞뒤 공백도 친 그대로 넘긴다. `raw_*` 는 손대지 않는다.

## 5. 다른 칸에도 같은 문제가 있었나

**실제로 깨진 것은 품목 표시명과 규격 둘뿐이다.** 이 둘만 매 타건마다 서버를 다녀왔다.

| 칸 | 예전 구조 | 그때 상태 |
|---|---|---|
| 품목 표시명 · 규격 | 타건마다 서버 저장 + 되읽기 | **깨짐** |
| 품의 내용 문구 | 로컬 상태, 단추로 저장 | 안 깨짐 (다만 바깥 값이 바뀌어도 안 따라감) |
| 부서 설정 5개 칸 | 로컬 상태만 | 안 깨짐 |
| 확인 사유 | 로컬 상태만 | 안 깨짐 |
| 저장 폴더 | 로컬 상태만 | 안 깨짐 |
| 수량·단가·금액 | `defaultValue` + `onBlur` | 안 깨짐 (대신 바깥 값이 바뀌어도 안 따라감) |

안 깨지던 칸도 **모두 `TextField` 로 바꿨다.** 나중에 누가 "저장하면서 목록을 새로 읽는" 코드를
한 줄 넣는 순간 같은 버그가 되살아나기 때문이다. 덤으로 `defaultValue` 칸들이
바깥 값 변화를 못 따라가던 잠재 문제도 함께 사라졌다.

## 6. 확인한 것

### 6-1. 자동 시험 (`npm run check:model`)

`scripts/check-ime.ts` 가 브라우저가 만드는 **사건 흐름**을 그대로 흘려 넣는다.

- 사용자가 말한 네 문자열: `방과후 기초Yap! 상` · `드론항공과학 교구세트` ·
  `바둑교재(상상바둑)` · `토탈공예미니어처`
- 각 문자열을 **조용히 칠 때**와 **글자마다 바깥 값이 끼어들 때** 두 가지로 모두 확인
- 조합 중 Backspace · 확정 뒤 Backspace · 한글/영문 전환 · 한글+숫자+기호 섞어 치기
- 빠른 연속 입력(조합 사건이 겹쳐 들어오는 경우)
- 초점 이동으로 확정 · Enter 로 확정 · **같은 값을 두 번 저장하지 않음**
- 앞뒤 공백을 다듬지 않음

### 6-2. 실제 컴포넌트 (브라우저에서 조합 이벤트 주입)

임시 시험대에 **실제 `TextField`** 를 띄우고 `compositionstart` / `input(isComposing)` /
`compositionend` 를 진짜로 발생시켰다. 버그가 났던 구조(타건마다 비동기 저장 후 value 재주입)도
나란히 두고 비교했다.

| | 확정·저장 횟수 | 결과 |
|---|---|---|
| 고친 `TextField` | **1회** | `방과후 기초Yap! 상` |
| 버그가 났던 구조 | **27회** (조합 중간마다) | 자료를 27번 덮어씀 |

조합 도중 바깥 값을 억지로 밀어 넣어도 칸의 글자가 그대로 남는 것도 확인했다.
시험대는 확인 뒤 지웠다(제품에 들어가지 않는다).

### 6-3. 실제 앱

사용자 시험에서 깨져 있던 주산암산 품목 네 개를 새 입력칸으로 고쳐 저장하고 DB 로 확인했다.

```
#4  표시명="방과후 기초Yap! 상"   원문=""  수정=1
#8  표시명="방과후 기초Yap! 하"   원문=""  수정=1
#9  표시명="10급Yap!"            원문=""  수정=1
#10 표시명="암산교재"             원문=""  수정=1
```

문구도 `주산암산부 방과후 기초Yap! 상 외 3종` 으로 제대로 다시 만들어졌다.
견적서에서 읽은 품목들(`#1`~`#3`)의 `raw_name` 은 **그대로**다.

## 7. 자동으로는 확인할 수 없는 것

**진짜 Windows 한국어 IME 로 치는 것**은 자동으로 재현하지 못했다.
바깥 프로세스에서 `ImmSetConversionStatus` 로 WebView2 안의 IME 를 바꿀 수 없기 때문이다.
그래서 **조합 사건 흐름**까지만 자동으로 확인했고, 실제 IME 조작은 사람이 해야 한다.

사용자가 직접 확인할 항목은 `04-P1-진행기록.md` 10장에 적었다.
