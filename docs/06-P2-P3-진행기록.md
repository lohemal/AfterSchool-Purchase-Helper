> **한 줄 요약** — 견적서 입력 형식을 PDF(글자)·PDF(스캔)·사진까지 넓혔다.

> **2026-09-13 실사용 시험 완료 — P2·P3 확정.**

> 일부 오인식된 품목·행이 있었으나 **추출 결과 확인 화면에서 사람이 곧바로 알아보고

## 0. 이 기능의 목표 수준 (2026-09-13 사용자 확정)

**견적서를 100% 무인 자동 처리하는 것이 목표가 아니다.**

> 견적서 내용을 최대한 자동으로 뽑아 **손으로 치는 일을 크게 줄이고**,
> 추출 결과 확인 화면에서 **사람이 마지막으로 확인·수정한 뒤** 회계 처리한다.

여기서 따라 나오는 규칙이 있다.

- 품목 몇 개를 잘못 읽었다는 이유만으로 **전체를 인식 실패로 처리하지 않는다.**
  읽은 것은 보여 주고, 불확실하거나 틀린 줄은 사람이 고치거나 지운다.
- 정확도를 올리려고 **외부 AI API 나 새 대형 의존성을 넣지 않는다.**
- 그래서 OCR 결과는 언제나 `확인 필요` 이상에서 시작한다. 프로그램이 혼자 확정하지 않는다.

## 3. PDF 판정 방식 — 확장자로 정하지 않는다

`quote/pdf_text.rs::probe()` 가 **먼저 글자를 뽑아 보고** 정한다.

```
PDF 열기
 → 글자 조각이 20개 미만이면        → 스캔본 (OCR 경로)
 → 쪽마다 표를 복원해 본다
      열 이름 낱말 3개 이상  그리고
      숫자 칸 4개 이상          → 텍스트 PDF (P2 경로)
 → 그 밖                          → 스캔본 (OCR 경로)
```

- 글자가 조금 나온다는 이유만으로 텍스트 PDF 라고 하지 않는다.
- 텍스트 PDF 판정에 실패해도 **거기서 끝내지 않고** OCR 후보로 넘긴다.
  실제 시험에서 스캔 PDF 는 `조각 0개 → 스캔본` 으로, 한글이 만든 PDF 는 `텍스트` 로 갈렸다.
- 왜 그렇게 갈렸는지를 사람 말로 남겨 화면에 보여 준다
  (`PDF 안에서 글자를 거의 찾지 못했습니다(조각 0개). 스캔본으로 보입니다.`).

## 4. OCR 전처리

- **3배 확대는 선택이 아니라 기본값이다** (`ocr::SCALE = 3`). P0-6 실측에서 원본 배율은 품목명 0/4, 3배는 4/4 였다.
- 한 변이 10,000픽셀을 넘지 않는 선에서 배율을 낮춘다(그 이상은 Windows OCR 이 받지 않는다).
- **원본 그림 파일은 열기만 하고 절대 쓰지 않는다.** 확대본은 메모리에만 있고 저장하지 않는다.
  시험이 원본 파일 크기가 그대로인지 확인한다.
- 확대본 좌표로 인식한 뒤 **좌표를 원본 기준으로 되돌린다**(배율로 나눈다). 화면에 보여 줄 위치가 원본과 맞아야 한다.

### 낱말이 아니라 **줄** 단위로 받는다

P3 에서 처음에 `OcrWord` 단위로 받았더니 표를 전혀 알아보지 못했다(`OCR_NO_TABLE`).
진단해 보니 품명이 `방과후` / `기초Yap!` / `상` 으로, 머리글이 `품` / `명/규` / `격` 으로 쪼개져 있었다.
`OcrLine` 단위(글자는 `Line.Text()`, 상자는 그 줄 낱말 상자들의 합)로 바꾸니 칸 하나가 줄 하나로 떨어졌다.
**P0-6 에서 검증한 것도 줄 단위였다.**

## 5. 표 복원 방식 (`quote/layout.rs` — PDF 와 사진이 같이 쓴다)

설계안 6-3 의 순서를 그대로 따른다.

1. 가까운 조각을 먼저 붙인다 (`merge_adjacent`)
2. y 로 행을 묶는다 (허용치 = 중앙 글자높이 × 0.6)
3. 머리글 행을 찾는다 (열 이름 낱말이 가장 많이 맞는 행)
4. **본문 행의 x 구간을 겹침으로 군집화해 열을 만든다**
5. 각 열 군집 중심에 **가장 가까운 머리글 이름을 나중에 붙인다**
6. 열 역할 결정 → 행 분류 → 숫자 정규화 → 합계 → 할인 부호 검산 (전부 **기존 `table.rs`**)

④ 와 ⑤ 의 방향이 반대라는 점이 핵심이다. **열은 자료가 정하고 이름만 머리글에서 가져온다.**
머리글 위치로 열을 나누면 왼쪽 정렬된 짧은 품명(`10급Yap!` · `암산교재`)이 앞 열로 끌려간다.

### 이번에 새로 붙인 두 가지

**(가) 조각 붙이기는 줄 안에서 왼쪽부터** — 실제 OCR 은 같은 줄이어도 글자마다 높이가 1픽셀씩 다르다.
y 중심만으로 줄세우면 오른쪽 끝 조각 뒤에 왼쪽 끝 조각이 와서 간격이 **음수**가 되고,
멀리 떨어진 칸이 하나로 붙는다. 실제 주산암산 JPG 에서 머리글의 `고` 와 `순번` 이 통째로 붙어
표를 못 알아봤다. 이제 **줄로 먼저 묶고 그 안에서 x 순서로** 붙이며, 오른쪽으로 이어질 때만 붙인다.

**(나) 머리글은 열 이름 사전으로 다시 붙인다** (`join_header_words`) — 한글이 만든 PDF 는
머리글을 칸 너비에 맞춰 벌려 쓴다. 실측에서 같은 칸 안 `품`↔`명` 간격이 46픽셀인데
옆 칸으로 넘어가는 `격`↔`수` 간격은 8픽셀이었다. **거리로는 절대 나눌 수 없다.**
그래서 머리글 행에 한해 `품`+`명` = `품명` 처럼 **사전에 있는 낱말이 정확히 만들어질 때만** 붙인다.
`품`+`절`+`수` 같은 없는 말은 만들지 않고, 6글자 높이보다 멀리 떨어진 조각은 끌어오지 않는다.

## 6. 신뢰 · 경고 기준 (`quote/trust.rs`)

### 읽어 온 경로

| `source` | 뜻 | 품목 신뢰도 상한 |
|---|---|---|
| `structured` | XLSX · XLS · XLSM · HWP · HWPX | `high` |
| `pdf_text` | PDF 안의 글자를 좌표로 되살림 | `high` (좌표가 정확하면 값도 정확하다) |
| `ocr` | 사진 · 스캔 PDF | **`medium` 까지.** 사람이 한 번은 봐야 한다 |

### 한 줄 상태 네 가지

| 상태 | 언제 | 화면 |
|---|---|---|
| 정상 `ok` | 경고 없음 | 초록 |
| 확인 필요 `needs_check` | 사진에서 읽었다 / 합계를 못 찾았다 | 노랑 |
| 인식 불확실 `uncertain` | 열을 못 찾았다 / 글자가 깨졌다 | 노랑 |
| 금액 검증 실패 `amount_failed` | 수량×단가 ≠ 금액, 또는 표기 합계와 품목 합이 다르다 | 빨강 |

**나쁜 쪽이 이긴다.** 사진에서 읽은 것은 절대 `정상` 으로 시작하지 않는다.

### 근거는 계산으로만 만든다

Windows OCR 은 낱말 신뢰도를 주지 않는다. **가짜 확률값을 만들지 않는다.** 쓰는 근거는 이것뿐이다.

- 필요한 열(품명·금액)을 찾았는가
- 행마다 `수량 × 단가 == 금액` 이 성립하는가
- 표기 합계와 품목 합이 맞는가
- 글자에 한글 자모 낱자·사용자 정의 영역 글자가 섞였는가

### 값은 절대 고치지 않는다

사용자가 든 예를 시험으로 못 박았다(`amount_mismatch_is_reported_not_fixed`).

```
수량 3 · 단가 10,000 · 금액 80,000
→ 금액은 80,000 그대로 둔다. 30,000 으로 고치지 않는다.
→ 상태: 금액 검증 실패
```

### 깨져 읽힌 합계는 **고치지 않고 쓰지 않는다**

실제 주산암산 사진에서 `₩68,000` 이 `鬧8,000` 으로 읽혔다. 그대로 믿으면 견적 총액이 8,000원이 된다.

- 68,000 으로 되돌리는 것은 추정이므로 **하지 않는다.**
- 대신 **숫자 바로 앞뒤에 다른 글자가 붙어 있으면 온전히 읽힌 숫자가 아니다** 로 판정한다
  (`number_looks_broken`). 통화 기호·괄호·부호·`원` 은 붙어도 된다.
- 이때 **읽은 값(8,000)과 원문(`鬧8,000`)을 지우지 않고 화면에 그대로 보여 주면서**,
  정산과 비교할 값만 품목 합으로 바꾸고 `확인 필요` 로 표시한다.
- 깨끗하게 읽힌 합계가 품목 합과 다르면 그때는 **금액 검증 실패**다(비교 기준을 몰래 바꾸지 않는다).
- **품목 합조차 검증되지 않으면 정상으로 두지 않는다.** 표기 합계를 쓰지 못해 품목 합으로 비교하는데
  그 품목 합도 `수량×단가` 로 맞춰 볼 수 없다면 대조할 것이 하나도 없다는 뜻이므로
  `인식 불확실` 로 내린다(`OCR_TOTAL_UNVERIFIED`).
- 이 규칙은 **사진 경로에서만** 돈다. XLSX·HWP 는 P1 그대로다(`structured_totals_are_never_set_aside`).

> **2026-09-13 사용자 승인.** 위 처리 방식을 그대로 쓰기로 확정했다.
> 추정·보정 금지, 원문 보존, 화면에서 원문 확인 가능, 비교 기준은 정상 품목의 금액 합,
> 상태는 `확인 필요`, 단 품목 합도 검증 안 되면 정상 아님 — 모두 승인된 내용이다.

## 8. 처리 시간

| 파일 | 걸린 시간 |
|---|---|
| 주산암산 JPG (794×1123 → 3배) | **6.3 ~ 7.2초** |
| 주산암산 스캔 PDF (그림 꺼내기 + OCR) | **약 8초** |
| 로봇과학 텍스트 PDF | 1초 미만 |

P0 탐침 때는 21~22초였다. 제품 경로가 더 빠른 것은 확대본을 파일로 쓰지 않고 메모리로만 넘기기 때문이다.
그래도 **화면이 멈춘 것처럼 보이면 안 되므로** 진행 상태를 반드시 보여 준다.

- 견적서 읽기는 Tauri 명령이라 **UI 스레드가 아닌 작업 스레드에서** 돈다.
- 파일마다 `quote-progress` 사건을 보낸다: `start` → `done` 또는 `failed`.
  화면에는 `(2/5) 주산암산 견적서.jpg — 글자를 알아보는 중입니다. 한 장에 20초쯤 걸립니다.` 로 나온다.
- 읽는 동안 파일 고르기 단추는 잠기고 `읽는 중…` 으로 바뀐다.
- `원본에서 다시 읽기` 도 같은 알림을 쓴다.
- **정확도를 깎아 시간을 줄이지 않았다.** 3배 확대는 그대로다.

## 9. 실패했을 때 (fallback)

**작업 전체가 막히면 안 된다.** P1 의 "읽지 못함 → 직접 입력" 길을 그대로 둔다.

| 어디서 | 무슨 일 | 어떻게 되는가 |
|---|---|---|
| PDF 글자 부족 | 텍스트 PDF 아님 | 실패로 끝내지 않고 **OCR 경로로 넘긴다** |
| 스캔 PDF 에 그림 없음 | `PDF 에서 글자도 그림도 찾지 못했습니다` | 등록은 남고 직접 입력 |
| 사진에 글자 없음 | `사진에서 글자를 찾지 못했습니다` | 등록은 남고 직접 입력 |
| 표를 못 알아봄 | `자동 인식에 실패했습니다. … 품목을 직접 입력할 수 있습니다.` | 등록은 남고 직접 입력 |
| 한국어 OCR 없는 PC | 설정에서 광학 문자 인식을 더하라고 안내 | 다른 형식은 그대로 |

`unreadable_quote_does_not_block_the_work` 시험이 글자 없는 흰 사진을 넣어
"등록은 남고 · 거래처 매칭은 파일명으로 되고 · 품목을 손으로 넣을 수 있다" 를 확인한다.
**OCR 실패는 프로그램 오류와 구분해서 보여 준다.**

## 11. 새로 발견한 위험

## 12. 남은 제한사항

1. **업무에서 실제로 받은 텍스트 PDF 견적서 샘플이 아직 없다.**
   지금 시험은 한글이 내보낸 PDF 다. 거래처가 다른 프로그램(아래아한글 외 · 회계 프로그램 · 웹 출력)으로
   만든 PDF 는 머리글을 다르게 벌려 쓸 수 있다. **실제 PDF 견적서를 한 장 받아 다시 확인해야 한다.**
2. **스캔 PDF 시험은 사람이 만든 스캔본이 아니다.** 실제 복합기 스캔본(기울기·그림자·JBIG2 압축)은
   아직 넣어 보지 못했다. 기울기 보정(`TextAngle` 재인식)은 넣지 않았다.
3. **한 쪽에 그림이 여러 장인 스캔본**은 가장 큰 그림 하나만 쓴다. 쪽을 반씩 나눠 스캔한 문서는 놓친다.
4. **여러 쪽 스캔본에서 견적서가 아닌 쪽**은 제목(`견적서`/`납품서`)으로만 가른다.
   제목이 깨져 읽히면 사람이 골라야 한다.
5. **Windows 한국어 OCR 이 없는 PC** 에서는 사진·스캔 PDF 를 못 읽는다. 안내만 하고 막지는 않는다.
6. **C5 · C6 은 여전히 미확정**이다. P2·P3 는 이 둘에 기대지 않는다.
7. 화면에서 **원본 그림을 나란히 보여 주는 기능**은 아직 없다(설계안 5장). 지금은 원본 위치(`사진`·`N쪽`)만 알려 준다.
