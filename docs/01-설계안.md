## 1. 요구사항 요약

1. 입력 셋. ① 부서·거래처 설정(앱에 보존) ② 거래처별 견적서(형식 제각각) ③ 정산자료 XLSX(고정 양식).
2. 견적서에서 품목(물품명·규격·수량·단가·금액)과 합계를 뽑는다. 뽑은 값은 **검토·검증용 근거**이고, 최종 파일에 품목 단가·수량이 그대로 들어가지는 않는다.
3. 최종 산출물은 재원(수익자·초과금·지원금·자유수강권)별 XLSX 최대 4개. 시트명 `품목내역`, 열 `내용 | 규격 | 수량 | 예상단가`.
   한 거래처 묶음이 한 행이 되고 `규격=식`, `수량=1`, `예상단가=그 재원 금액`.
4. `내용` 문구는 `품의 표기명 + 대표품목 + ("1종" | "외 N종")` 으로 자동 생성하고, 대표품목·문구 모두 사용자가 고칠 수 있다.
5. 견적서 합계와 정산 금액이 맞는지 검증하고, 불일치는 고치지 않고 경고한다. **원본 값은 프로그램이 절대 바꾸지 않는다.**
6. 흐름은 한 방향 위저드이며, 불확실한 값은 눈에 띄게 표시한다.
7. 로컬 처리, 외부 AI·API 없음, 오프라인 동작. Tauri 2 + React + TS + Rust + SQLite.

## 2. 용어 — 이 문서에서 가장 중요한 장

실제 자료에서 **이름 모양이 같지만 뜻이 전혀 다른 두 가지**가 발견됐다. 섞이면 금액이 틀린다.

### 2-1. 세 가지 이름을 절대 섞지 않는다

| 용어 | 뜻 | 예 | 어디서 오는가 |
|---|---|---|---|
| **품의 부서** | 품의 문구에 나타나는 단위 | `토탈공예미니어처`, `키즈쿠킹`, `로봇과학`, `바둑` | 사용자가 부서 설정에서 등록 |
| **정산 별칭** | 정산자료 `부서명` 열에 실제로 적히는 이름. **강좌·반·요일이 나뉜 원자료 이름일 뿐이다** | `토탈공예미니어처`, `토탈공예미니어처1`, `토탈공예미니어처2`, `목요키즈쿠킹`, `화요키즈쿠킹` | 정산자료 원문. 사용자가 품의 부서에 붙여 준다 |
| **거래처 관리명** | 견적서 한 장 = 품의 한 행의 단위. **거래처를 구분한다** | `로봇과학1`, `로봇과학2`, `바둑` | 사용자가 부서 설정에서 등록. 견적서 파일명에 넣는다 |

> **`토탈공예미니어처1` 의 `1` 과 `로봇과학1` 의 `1` 은 완전히 다른 뜻이다.**
> 앞의 것은 원자료의 강좌 구분이고 품의에서는 도로 합쳐진다. 뒤의 것은 거래처 구분이고 품의에서 따로 나뉜다.
> **프로그램은 숫자 접미사를 해석하지 않는다.** 두 이름 모두 사용자가 등록한 표에서만 뜻을 얻는다.

### 2-2. 두 방향의 관계

```
정산자료 여러 줄  ──합산(자동)──▶  품의 부서  ──나눔(사용자 입력)──▶  거래처 관리 단위 = 품의 행
  토탈공예미니어처  115,000                                              (거래처 1곳이면 그대로)
  토탈공예미니어처1 460,000   ──▶  토탈공예미니어처  690,000  ──▶  토탈공예미니어처(1곳)  690,000
  토탈공예미니어처2 115,000

  로봇과학 810,000           ──▶  로봇과학 810,000        ──▶  로봇과학1  720,000  ← 사용자 입력
                                                              로봇과학2   90,000  ← 사용자 입력
```

- **왼쪽(합산)은 자동**이다. 같은 품의 부서로 매핑된 정산 별칭들의 재원별 금액을 더한다.
- **오른쪽(나눔)은 자동이 아니다.** 거래처가 둘 이상이면 사용자가 재원 4칸을 각각 입력한다.
  견적 금액 비율 등으로 추정하지 않는다. 거래처가 하나면 부서 금액을 그대로 쓴다(자동).

### 2-3. 그 밖의 용어

- **품의 표기명** — 문구 접두. 기본값은 `품의 부서명 + "부"` 이고 사용자가 고칠 수 있다.
  (`목요키즈쿠킹`·`화요키즈쿠킹` → `키즈쿠킹부` 처럼 기계적으로 만들 수 없는 경우가 실재한다.)
- **재원** — `수익자` · `초과금` · `지원금` · `자유수강권` 네 가지. 정산자료의 네 열이고 최종 파일 네 개다.
- **작업** — 한 번의 품의 묶음. 예: `2026학년도 9월 교재비`.

- **모든 형식은 `RawTable`(문자열 격자 + 셀 출처)로 정규화한 뒤 하나의 `table.rs` 가 품목을 뽑는다.** 새 형식 추가 = 파서 하나 추가.
- 파싱·검증·생성은 Rust. 순수 계산 로직은 `src/lib/*.ts` 에 두어 `scripts/check-*.ts` 로 시험한다.
- 한글 COM 은 전용 스레드 + 시간 제한 + TEMP 경유 + 잔류 프로세스 정리(문서 통합 도구의 검증된 방식).

```

  -- 사용자가 화면에서 고쳤을 때만 raw_name 과 달라진다.

  id, work_id, row_no

  department_id             별칭 해석 결과 (NULL = 미등록 별칭)
  beneficiary, excess, subsidy, voucher        원 단위 정수

work_allocation             거래처별 재원 배분 = 품의 한 행의 금액
  id, work_id, vendor_unit_id                  UNIQUE(work_id, vendor_unit_id)
  beneficiary, excess, subsidy, voucher
  source(auto|manual)       거래처가 하나면 auto(부서 합 그대로), 둘 이상이면 manual
  updated_at

work_check                  검증 결과 + 사용자 확인
  id, work_id, kind, department_id, vendor_unit_id
  expected, actual, diff, status(ok|warn|error)
  acknowledged, ack_reason, ack_at

work_output                 생성 기록
  id, work_id, fund, path, row_count, total, created_at, verified
```

- 금액은 전부 **원 단위 정수(i64)**. 부동소수를 쓰지 않는다.
- 품의 한 행 = `work_allocation` 한 줄 + 그 거래처의 `work_quote`(문구). 별도의 "품의 항목" 표는 필요 없다.
- **위 표가 곧 14장 15번의 보존 목록이다.** 프로그램을 껐다 켜도 `work` 를 골라 이어서 진행할 수 있다.
- 원본 견적서는 복사하지 않는다. **경로·크기·해시만** 두고, 파일이 옮겨지거나 지워지면 "원본 없음" 으로 표시하되
  **이미 추출해 저장한 작업 데이터는 그대로 유지된다**(작업은 계속 진행할 수 있다).

### 4-3. 파싱 결과 모델 (Rust ↔ TS, serde)

```ts
type Confidence = 'high' | 'medium' | 'low';     // OCR 은 수치를 안 주므로 3단계

interface Quote {
  sourceFile: string; format: QuoteFormat;
  vendorUnitId?: number; matchCandidates: number[]; matchMethod: 'auto'|'manual'|'none';
  vendorNameInDoc?: string;                       // 견적서 안의 상호 (참고용)
  items: QuoteItem[];
  supplyTotal?: Money; taxTotal?: Money; grandTotal?: Money;   // 견적서에 적힌 값
  itemSum: Money;                                  // kind==='item' 금액의 합
  adjustmentSum: Money;                            // kind==='adjustment' 를 signEffect 대로 적용한 합
  computedTotal: Money;                            // itemSum + adjustmentSum
  compareBasis: 'grand'|'supply'|'computedTotal';
  warnings: Warning[]; confidence: Confidence;
  representativeItemIndex: number;
  contentPhraseAuto: string; contentPhraseOverride?: string;
}
type RowKind = 'item' | 'adjustment' | 'zero';    // 합계·빈 행은 품목 목록에 담지 않는다
type SignEffect = 'as_written' | 'subtract' | 'unknown';

interface QuoteItem {
  kind: RowKind;                                  // 'item' 만 N종·대표품목에 쓴다
  signEffect?: SignEffect;                        // kind==='adjustment' 일 때만
  displayName: string;                            // 품의 문구에 쓸 이름. 기본값 = raw.name
  spec?: string; qty?: number; unitPrice?: Money; amount?: Money;   // amount 는 원문 부호 그대로
  raw: { name?: string; spec?: string; qty?: string; unitPrice?: string; amount?: string };
  cellRef?: string;                               // 근거 셀/좌표 (검토 화면 강조용)
  warnings: Warning[]; confidence: Confidence;
}
// WarningCode: QTY_PRICE_MISMATCH, ITEM_SUM_NE_TOTAL, TOTAL_NOT_FOUND, HEADER_AMBIGUOUS,
//   NUMBER_UNPARSED, OCR_LOW_TRUST, MULTIPLE_TABLES, TABLE_PICKED_BY_TITLE, EMPTY_NAME,
//   ADJUSTMENT_SIGN_UNKNOWN, ...
```

### 4-4. 상태 표기

| 상태 | 뜻 | 색 |
|---|---|---|
| 정상 | 경고 없음, 매칭·검증 통과 | 초록 |
| 주의 | info 급 (세액 열 없음, 합계 행 없음 등) | 노랑 |
| 확인 필요 | warn 급 (수량×단가 불일치, OCR 값, 머리글 애매, 표 여럿) | 주황 |
| 금액 불일치 | 세로 합 또는 가로 합이 맞지 않음 | 빨강 |
| 배분 미입력 | 거래처 둘 이상인데 배분을 아직 안 넣음 | 빨강 |
| 거래처 매칭 실패 | 관리명 미지정 또는 후보 복수 | 빨강 |
| 미등록 별칭 | 정산자료 이름이 어느 부서에도 안 붙음 | 빨강 |
| 정산 없음 / 견적 없음 | 한쪽만 있음 | 빨강 |

작업 전체 상태 = 가장 나쁜 행 상태. **빨강이 하나라도 있으면 생성이 잠긴다**(14장 13번).
잠금을 푸는 길은 하나뿐이다 — 빨강인 항목마다 사용자가 **[확인함] 을 누르고 사유를 한 줄 적는다**(공란 불가).
사유는 작업 데이터에 남고 **생성되는 XLSX 에는 들어가지 않는다.** "항상 허용" 설정은 없다.

## 5. 화면 구성

왼쪽 세로 단계 목록 + 오른쪽 내용. 단계마다 상태 요약(정상 n · 확인 필요 n · 오류 n)을 이름 옆에 표시하고,
넘어갈 수 없으면 잠금 표시와 이유를 적는다.

### 5-0. 글자 입력은 모두 공통 `TextField` 를 쓴다 (한글 조합 보호)

한국어 IME 는 `ㅂ → 바 → 방` 처럼 **조합 중인 임시 글자**를 칸에 올려 둔다.
이때 바깥에서 `value` 를 다시 써 넣으면 조합 버퍼와 칸의 값이 어긋나 자모가 갈라져 들어간다.

그래서 사용자가 글자를 칠 수 있는 칸은 **예외 없이 `components/TextField.tsx`** 를 쓴다.

- 치는 동안에는 **화면 값만** 바꾼다. 저장하지 않는다.
- **조합 중에는 바깥 값을 절대 받아들이지 않는다.**
- 초점을 잃거나 Enter 를 눌렀을 때 **한 번만** 확정한다.
- 글자를 다듬지 않는다(앞뒤 공백도 친 그대로). `raw_*` 는 어느 경우에도 바뀌지 않는다.

규칙은 `lib/imeText.ts` 에 순수 함수(상태 기계)로 있고 `scripts/check-ime.ts` 가 지킨다.

1. **부서 설정** — 세 표를 한 화면에서 다룬다.
   - 품의 부서 (표시명 · 품의 표기명 · 순서)
   - 그 부서의 **정산 별칭** 목록 (정산자료에 나오는 이름들)
   - 그 부서의 **거래처 관리 단위** 목록 (관리명 · 거래처명)
   - 두 목록이 나란히 보이고 각각 "정산자료에서 합쳐질 이름" · "견적서 파일명에 넣을 이름" 이라고 적어 둔다.
   - 가져오기/내보내기(JSON).
2. **견적서 등록** — 파일·폴더 끌어놓기. 표: 파일명 · 형식 · 관리명(드롭다운, 자동 매칭은 회색 "자동") · 상태.
   같은 관리명에 두 파일이 붙으면 오류.
3. **추출 결과 확인** — 왼쪽 견적 목록, 오른쪽에 품목 표(편집 가능, 경고 셀 강조, 원본값 툴팁) ·
   합계 상자(공급가액·세액·합계금액·품목 합·조정 합·계산 총액, 비교 기준 선택) · 대표품목 라디오 ·
   내용 문구(자동/수정/되돌리기) · 원본 보기. 행 추가·삭제.
   - 행마다 **종류**(`일반 품목` / `할인·조정` / `금액 0원`)를 바꿀 수 있다. 할인 행과 0원 행은 회색 줄로 구분되고
     `N종` 세기와 대표품목 라디오에서 빠진다. 0원 행에는 "참고 · 금액 0" 이라고 적는다.
   - 할인 행의 **부호 반영 방식**(원문 그대로 / 빼기)을 고를 수 있고, 자동 판별 결과가 미리 골라져 있다.
     어느 쪽으로 바꾸든 원문 값은 표에 그대로 남는다.
   - **품목명은 원문과 품의 표시명 두 칸으로 보인다.** 표시명만 고칠 수 있고, 고치면 "수정됨" 표시와
     원문으로 되돌리는 단추가 생긴다(6-5).
4. **정산자료 등록** — 파일 선택 → 읽은 표 표시 → 각 줄의 원문 이름을 별칭 표로 해석해 품의 부서를 붙인다.
   미등록 이름은 빨강으로 띄우고 그 자리에서 부서에 붙일 수 있다(부서 설정에 저장되어 다음 달에 재사용된다).
   부서별 합산 결과(재원 4칸)를 함께 보여 준다.
5. **금액 배분·검증** — 부서마다 아래 격자를 보여 준다. 거래처가 하나면 값이 자동으로 채워지고 편집이 잠긴다.

   ```
                   수익자     초과금    지원금    자유수강권      합계        견적 총액    가로 검증
   로봇과학1        [입력]    [입력]    [입력]     [입력]       자동        900,000      ✔/✘
   로봇과학2        [입력]    [입력]    [입력]     [입력]       자동        360,000      ✔/✘
   ─────────────────────────────────────────────────────────────────────────────────
   정산자료 합계    810,000    6,200   443,800        0      1,260,000
   세로 검증          ✔/✘      ✔/✘      ✔/✘       ✔/✘
   ```

   세로·가로가 모두 맞아야 초록이 된다. 어긋나면 차액을 보여 주되 **자동으로 채우거나 고치지 않는다.**
6. **품의자료 미리보기** — 재원별 탭 4개. 각 탭에 최종 표(내용·규격·수량·예상단가)와 합계. 0건 탭은 "생성 안 함" 표시.
7. **Excel 생성** — 저장 폴더(마지막 폴더 기억) · 파일 이름 미리보기 · [생성]. 생성 뒤 다시 읽어 검증한 결과와 [폴더 열기].

## 6. 파일 형식별 파싱 전략

| 형식 | 방법 | 안정성 | 단계 |
|---|---|---|---|
| **XLSX / XLSM / XLS** | calamine 으로 셀 격자, 병합은 sheet XML 로 보정, 수식은 저장된 계산값 | **높음** | P1 |
| **HWPX** | zip 안 `Contents/section*.xml` 의 `hp:tbl` → `hp:tr` → `hp:tc`, **`cellAddr` 로 격자 복원**(차례로 세면 병합 때문에 어긋난다) | **높음** | P1 |
| **HWP (5.x)** | 한글 COM 으로 열어 HWPX 저장 → 위 파서. 한글이 없는 PC 는 미지원 안내 | **높음(한글 필요)** | P1 |
| **텍스트 PDF** | 글자와 좌표 추출 → 아래 6-2 의 좌표 방식 | 중간 | P2 |
| **이미지 / 스캔 PDF** | Windows OCR(ko) → 아래 6-2 | 중간 | P3 |

### 6-1. 공통 표 해석 (`table.rs`)

1. **표 고르기** — 표가 여럿이면 **제목 글자로 고른다**(`견적서` 우선, `납품서`·`거래명세서`는 뒤로).
   실제 샘플에 견적서와 납품서가 **내용까지 똑같이** 들어 있어서, "품목 행이 가장 많은 표" 로는 고를 수 없다.
   제목으로도 못 고르면 문서에서 먼저 나오는 표를 쓰고 `MULTIPLE_TABLES` 경고.
2. **머리글 찾기** — 낱말 사전으로 한 행에 둘 이상 맞는 행을 머리글로 본다. 행 번호를 고정하지 않는다(실제 샘플은 1·9·11행 제각각).
3. **열 역할** — 머리글 낱말 → 역할. 동의어를 넉넉히 둔다.
   `품명|품목|물품명|상품명|내역|품명/규격` → name, `규격|사양|**단위**` → spec,
   `수량` → qty, `단가` → unit_price, `금액|공급가액` → amount, `세액|부가세` → tax, `비고` → note.
   `품명/규격` 처럼 합쳐진 열은 name 으로만 쓰고 spec 은 비운다(경고 없음).
   머리글이 없거나 애매하면 값의 성질로 추정하고 `HEADER_AMBIGUOUS`.
4. **행 분류 — 네 종류로 나눈다** (6-2 참고). `일반 품목` · `할인/금액 조정` · `합계/소계` · `빈 행`.
   "이름이 있고 금액이 0보다 큰 행" 이라는 조건만으로는 **할인 행을 가를 수 없다.** 먼저 종류를 정하고,
   `일반 품목` 만 종수(`N종`)와 대표품목에 쓴다. 샘플 세 건은 조정 행이 없어 이 분류로도 결과가 같다.
5. **숫자 정규화** — `76,500원`, `₩76,500`, `10개`, `1 set`, `-30,000`, `△30,000`, `(30,000)` → 정수(**부호 보존**).
   못 읽으면 원문 보존 + `NUMBER_UNPARSED`.
   > **괄호 예외 (P0-5 에서 실제로 걸렸다).** 한글 견적서는 합계를 `(￦ 900,000 )` 로 적는다 — 음수가 아니다.
   > **괄호 안이 숫자·쉼표·마침표·공백뿐일 때만** 회계식 음수로 본다. `(30,000)`=음수, `(￦ 900,000 )`=양수.
6. **합계 추출** — 합계 행 + `합계금액|총액|합 계 금 액` 옆 숫자. 못 읽으면 `TOTAL_NOT_FOUND` 후
   **품목 합으로 대체하고 그 사실을 표시한다**(실제로 OCR 이 `₩68,000` 을 놓쳤고 품목 합은 정확했다).
7. **셀 출처 보존** — 값마다 원본 셀 주소·좌표를 남겨 검토 화면에서 근거를 보여 준다.

**구현 주의 (P0 에서 실측한 것)**

- **`calamine` 의 `Range` 는 A1 에서 시작하지 않는다.** "실제로 쓴 영역"이 기준이라 바둑 견적서는 엑셀 2행 2열부터다.
  원본 셀 주소를 화면에 보여주려면 **`range.start()` 를 더해 절대 좌표로** 바꿔야 한다.
- **병합된 열은 머리글 칸과 값 칸의 차례가 다르다.** 역할별로 **그 머리글 차례부터 다음 역할 머리글 차례 직전까지**를
  열 범위로 잡고 그 안에서 값이 있는 첫 칸을 쓴다. 병합 53개짜리 양식이 이 방식으로 정확히 읽혔다.
- **XLSX 스타일을 직접 읽을 때 `<xf .../>` 자기닫음 태그를 놓치면 스타일 번호가 통째로 밀린다.**
  `Event::Empty` 는 `End` 가 오지 않으므로 그 자리에서 담아야 한다.
- **색은 `rgb` · `indexed` · `theme` · `auto` 네 가지로 적힌다.** 비교·검증할 때는 **RGB 로 정규화**한다
  (`indexed="9"` 와 `rgb="FFFFFFFF"` 는 같은 흰색, `theme="1"` 과 색 미기재는 같은 기본 글자색).

### 6-2. 행 종류와 할인 행 처리

| 종류 | 판별 | `N종`·대표품목 | 견적 총액 | 저장·표시 |
|---|---|---|---|---|
| **일반 품목** | 이름이 있고 금액이 **0보다 크며** 아래에 해당하지 않음 | **포함** | 포함 | 저장 |
| **할인 / 금액 조정** | 이름이 조정 낱말과 맞거나(`할인·할인금액·DC·D/C·에누리·차감·조정·감액`) 금액이 음수 | **제외** | **포함** | 저장 |
| **금액 0원 행** | 이름은 있는데 금액이 **0** (사은품·증정 등) | **제외** | **영향 없음** | **저장하고 참고용으로 보여 준다** |
| **합계 / 소계** | 이름이 `합계·총계·소계·계·부가세·VAT` 와 맞음 | 제외 | 총액 추출에 사용 | 품목으로 저장 안 함 |
| **빈 행** | 이름과 금액이 모두 비어 있음 | 제외 | 제외 | 저장 안 함 |

**할인 행 규칙** (14장 9번)

- **원문 값을 그대로 읽어 보존한다.** 할인율·할인액을 추정하거나 계산하지 않는다.
  `할인 -30,000` 이면 `-30,000` 을, `할인 30,000` 이면 `30,000` 을 그대로 담는다. **프로그램이 부호를 바꾸지 않는다.**
- 양식마다 표기가 다르므로(`할인` · `할인금액` · `DC -30,000`) **부호가 총액에 어떻게 반영되는지는 검산으로 알아낸다.**
  `sign_effect` 를 이렇게 정한다.

  | 값 | 뜻 | 판별 |
  |---|---|---|
  | `as_written` | 원문 부호 그대로 더한다 | `Σ품목 + Σ조정(원문)` 이 견적서 표기 총액과 맞음 |
  | `subtract` | 양수로 적혀 있지만 빼는 값이다 | `Σ품목 − Σ\|조정\|` 이 표기 총액과 맞음 |
  | `unknown` | 표기 총액이 없거나 어느 쪽도 안 맞음 | `ADJUSTMENT_SIGN_UNKNOWN` 경고 → **사용자가 고른다** |

  어느 쪽으로 정해지든 **원문 값(`raw_amount`)은 건드리지 않는다.** `sign_effect` 는 계산에만 쓰는 별도 값이고 사용자가 바꿀 수 있다.
- 할인 행은 **대표품목 후보가 아니다.** 대표품목은 `일반 품목` 중 첫 행이다.
- 할인 행에는 `수량 × 단가 = 금액` 검증을 적용하지 않는다(수량·단가가 없는 것이 보통이다).

**금액 0원 행 규칙** (14장 10번)

- **사은품이든 아니든 금액이 0원인 행은 품목 수 계산에서 뺀다.** 대표품목 후보도 아니고 견적 총액에도 영향이 없다.
- 다만 **원본에 있는 행이므로 지우지 않는다.** 추출 결과 화면에 회색 줄로 남겨 "참고 · 금액 0" 이라고 표시한다.
- 행 종류는 **사은품이라는 이름이 아니라 금액이 0인지로** 정한다. `사은품`·`증정` 같은 낱말에 의존하지 않는다.
- 원본 값은 어떤 경우에도 고치거나 지우지 않는다. 사용자가 종류를 바꿔 품목으로 세게 할 수는 있다.

사용자 예시로 확인하면 이렇게 된다.

```
교재A     100,000   → 일반 품목
교재B     200,000   → 일반 품목
할인      -30,000   → 할인/금액 조정  (sign_effect = as_written, 300,000 + (-30,000) = 270,000 ✔)

품목수 2종 · 대표품목 교재A · 자동 문구 "○○부 교재A 외 1종" · 견적 총액 270,000
```

```
교재A     100,000   → 일반 품목
교재B     200,000   → 일반 품목
사은품 노트      0   → 금액 0원 행 (참고 표시, 계산에 영향 없음)

품목수 2종 · 대표품목 교재A · 자동 문구 "○○부 교재A 외 1종" · 품목 금액 300,000
```

### 6-3. 이미지·PDF 의 열 만들기 — 머리글 위치로 나누면 안 된다

실측에서 머리글 중심 최근접·머리글 중간점 두 방식 모두 깨졌다(왼쪽 정렬된 짧은 품명이 앞 열로 끌려간다).

**쓰는 방법**: ① y 로 행을 묶는다(허용치 = 중앙 글자높이 × 0.6) ② 머리글 행을 찾는다
③ **본문 행 블록들의 x 구간을 겹침으로 군집화해 열을 만든다**
④ 각 열 군집에 **그 군집 중심에서 가장 가까운 머리글 이름을 나중에 붙인다**.
이 순서로 주산암산 견적서의 6열이 정확히 복원됐다(P0-6 실측).
③ 과 ④ 의 방향이 반대라는 점이 중요하다 — **열은 자료가 정하고, 이름만 머리글에서 가져온다.**

**P2·P3 실측에서 두 가지를 더했다** (자세한 내용은 `docs/06-P2-P3-진행기록.md` 5장).

- **조각 붙이기는 줄 안에서 왼쪽부터.** 실제 OCR 은 같은 줄이어도 글자 높이가 1픽셀씩 다르다.
  y 중심만으로 줄세우면 오른쪽 끝 조각 뒤에 왼쪽 끝 조각이 와서 간격이 음수가 되고,
  멀리 떨어진 칸이 하나로 붙는다(주산암산 JPG 에서 `고`+`순번` 이 붙어 표를 못 알아봤다).
- **머리글은 열 이름 사전으로 다시 붙인다.** 한글이 만든 PDF 는 머리글을 칸 너비에 맞춰 벌려 쓴다.
  같은 칸 안 `품`↔`명` 간격이 46픽셀인데 옆 칸으로 넘어가는 `격`↔`수` 간격은 8픽셀이었다 —
  **거리로는 나눌 수 없다.** 사전에 있는 낱말이 정확히 만들어질 때만 붙이므로 없는 이름은 생기지 않는다.

### 6-4. 견적서 안의 거래처 정보

상호·사업자등록번호를 뽑아 참고로 보여 준다. **매칭에는 쓰지 않고** 품의 파일에도 들어가지 않는다.
등록된 거래처명과 다르면 "주의" 만 띄운다.

### 6-5. 품목명 — 원문과 품의 표시명을 나눈다

| 값 | 뜻 | 규칙 |
|---|---|---|
| `raw_name` | 견적서 원문 | **절대 바뀌지 않는다.** 파서가 읽은 그대로 |
| `display_name` | 품의 문구에 쓸 현재 이름 | **기본값 = `raw_name`.** 사용자가 화면에서 고쳤을 때만 달라진다 |

**프로그램은 `display_name` 에 어떤 가공도 하지 않는다** — 띄어쓰기 조정·축약·맞춤법 교정·괄호 제거 모두 안 한다.
자동 생성 문구는 언제나 `display_name` 을 쓴다.

```
바둑          raw_name = display_name = '바둑교재(상상바둑)'
              → 바둑부 바둑교재(상상바둑) 1종            (사용자가 손대지 않으면 이대로)

항공드론      raw_name = '드론항공과학교구세트'
              사용자가 display_name 을 '드론항공과학 교구세트' 로 고침
              → 항공드론부 드론항공과학 교구세트 1종
```

화면에는 두 값을 함께 보여 주고, 고친 행은 "수정됨" 으로 표시하며 원문으로 되돌리는 단추를 둔다.

### 6-6. 문구 생성

`품의 표기명 + " " + 대표품목 display_name + " " + ("1종" | "외 N종")`

- **품의 표기명은 모든 부서에 붙인다.** 접두를 빼는 예외는 두지 않는다(14장 11번).
- `N` = `kind === 'item'` 인 행의 개수. 할인 행과 금액 0원 행은 세지 않는다.
- 대표품목은 `kind === 'item'` 중 첫 행이 기본값이고 사용자가 바꿀 수 있다.
- 완성된 문구도 사용자가 직접 고칠 수 있다(`content_phrase_override`).

## 7. OCR 전략

**목표 수준 (2026-09-13 사용자 확정)** — 100% 무인 자동 처리가 아니다.
"손으로 치는 일을 크게 줄이고, 확인 화면에서 **사람이 마지막으로 확인·수정한 뒤** 회계 처리한다" 가 목표다.
그래서 품목 몇 개를 잘못 읽었다고 **전체를 실패로 처리하지 않는다.** 읽은 것은 보여 주고 사람이 고치거나 지운다.
정확도를 올리려고 외부 AI API 나 새 대형 의존성을 넣지 않는다.

- **엔진**: Windows 내장 OCR(`Windows.Media.Ocr`, `windows` 크레이트 WinRT). 설치·모델 파일·네트워크 없음.
- **입력은 항상 3배로 확대해 인식한다. 선택이 아니라 필수다.** 실측(P0-6): 원본 크기(794×1123)에서 품목명 **0/4**,
  3배에서 **4/4**·숫자 12/12 정확. 시험이 이 사실을 단언으로 못 박아 두었다.
  `image` 크레이트로 확대(OCR 최대 10000px), 필요하면 `TextAngle` 로 회전 보정 후 재인식.
- **신뢰도는 계산한다**(엔진이 주지 않는다): `수량×단가=금액` 성립, 열 합=합계 성립, 숫자 열의 비숫자 비율, 행마다 열 개수 일치.
  전부 성립하면 `medium`, 하나라도 어긋나면 `low`. **OCR 결과에는 `high` 를 주지 않는다.**
- **후처리**: `O→0, l→1, S→5` 같은 혼동 문자는 **후보로만 제시**하고 자동 교정하지 않는다. 원문은 항상 보존한다.
- **화면**: 이미지 견적은 항상 "확인 필요" 이상으로 시작하고, 사용자가 행마다 확인해야 "정상" 이 된다(XLSX·HWP 는 그렇지 않다).
- **낱말이 아니라 줄 단위로 받는다** (P3 실측). 낱말 단위로 받으면 품명(`방과후 기초Yap! 상`)과
  머리글(`품 명/규 격`)이 조각나 열을 만들 수 없다. 견적서 표에서는 칸 하나가 줄 하나로 떨어진다.
- **깨져 읽힌 합계는 쓰지 않는다** (P3 실측). `₩68,000` 이 `鬧8,000` 으로 읽혔다.
  되돌리는 것은 추정이므로 하지 않고, **숫자에 다른 글자가 붙어 있으면 못 읽은 것**으로 보아
  품목 합으로 비교하며 `확인 필요` 로 표시한다. 읽은 값과 원문은 지우지 않고 그대로 보여 준다.
  이 규칙은 사진 경로에서만 돈다.
- **엔진 교체 여지**: 읽어 오는 자리는 `quote/ocr/engine.rs` 한 곳뿐이다. 다른 엔진으로 바꾸려면 여기만 고친다.
- **학교 PC 에 한국어 OCR 이 없을 수 있다** → 없으면 안내만 하고 다른 기능은 그대로 쓴다.

## 8. 매칭 전략

### 8-1. 파일명 → 거래처 관리명

운영 규칙은 **"파일명에 최소한 부서명을 반드시 넣는다. 거래처가 여러 개인 부서는 거래처 관리명까지 넣는다"** 이다(14장 1번).
**파일명 형식을 강제하지 않는다.** 아래는 모두 맞는 이름이고 똑같이 매칭된다.

```
주산암산부 견적서.jpg     주산암산 견적서.jpg     주산암산 견적서류.jpg     주산암산 9월 견적서.jpg
```

`부` · `견적서` · `견적서류` · 월 표시 같은 **주변 글자는 매칭에 영향을 주지 않는다.**
판단 기준은 오직 **등록된 이름이 파일명 안에 들어 있는가**다.

1. 파일명(확장자 제외)을 정규화: 공백·`_`·`-`·괄호 제거, 전각→반각, 대소문자 무시.
2. **등록된 거래처 관리명**을 **길이 긴 것부터** 포함 검사.
   `로봇과학1견적서` 는 `로봇과학1` 에 맞고, 더 짧은 `로봇과학` 에는 맞추지 않는다.
3. 하나도 안 맞으면 **등록된 품의 부서명**으로 포함 검사.
4. 그 부서의 거래처가 **1개면 자동 매칭**한다. (`주산암산 견적서류.jpg` → 부서 `주산암산` → 거래처 하나 → 자동)
5. 그 부서의 거래처가 **2개 이상이면 추측하지 않는다.**
   **"로봇과학 부서는 거래처가 여러 개입니다"** 라고 표시하고 후보를 보여 사용자가 고르게 한다.
6. 부서명도 못 찾으면 수동 선택.

언제든 드롭다운으로 바꿀 수 있고, 바꾸면 `manual` 로 기록된다. 같은 거래처 관리 단위에 두 파일이 붙으면 오류다.

> **하지 않는 것 두 가지.**
> ① **정산 별칭은 파일명 매칭에 쓰지 않는다.** 쓰면 `토탈공예미니어처1 견적서.xlsx` 가 있지도 않은 거래처로 붙는다.
> ② **숫자 접미사를 떼거나 붙이지 않는다.** `로봇과학 견적서.hwp` 를 보고 `로봇과학1` 로 추측하지 않는다.

### 8-2. 정산자료 이름 → 품의 부서

- 정산자료 `부서명` 열의 원문을 **`settlement_alias` 표에서만** 찾는다. 문자열 규칙(숫자 떼기, 앞뒤 자르기)으로 추측하지 않는다.
- 못 찾으면 **미등록 별칭**(빨강)으로 띄우고 사용자가 부서에 붙인다. 붙인 내용은 부서 설정에 저장되어 다음 달에 재사용된다.
- 같은 부서로 붙은 줄들의 재원 4금액을 **자동 합산**해 부서 금액을 만든다.
- A열이 `합계` 인 마지막 행은 자료에서 제외하되, 열별 합이 그 행과 맞는지 **검산해 형식 확인에 쓴다**.
- 견적서가 있는데 부서 금액이 없으면 "정산 없음", 반대면 "견적 없음" 으로 표시한다.

### 8-3. 정산자료 형식 확인

머리글을 위에서 10행 안에서 낱말로 찾는다(행 번호를 고정하지 않는다). 필요한 열을 못 찾으면
"정산자료 형식이 다릅니다: 못 찾은 열 ○○" 로 **멈춘다**(추정하지 않는다).

## 9. 금액 검증 전략

| # | 검증 | 식 | 어긋날 때 |
|---|---|---|---|
| 1 | 행 | `수량 × 단가 == 금액` (`일반 품목` 행만. 할인 행·0원 행은 건너뛴다) | `QTY_PRICE_MISMATCH` warn. 10원 미만 차이는 info(절사). **자동 수정 없음** |
| 2 | 품목 합 | `Σ일반품목 + Σ조정(sign_effect 적용) == 견적서 표기 공급가액` (0원 행은 더해도 값이 같으므로 영향 없음) | warn |
| 2a | 조정 부호 | 위 식이 `as_written` 또는 `subtract` 중 하나로 맞는가 | 둘 다 아니면 `ADJUSTMENT_SIGN_UNKNOWN` warn → **사용자가 고른다.** 원문 값은 안 바꾼다 |
| 3 | 총액 | `공급가액 + 세액 == 합계금액` | warn. 세액 열이 없으면 생략 |
| 4 | **가로 (거래처별)** | `수익자+초과금+지원금+자유수강권 == 그 거래처 견적 총액` | **error** → 생성 잠김 |
| 5 | **세로 (재원별)** | `Σ거래처별 그 재원 == 부서의 정산 합계(재원별)` | **error** → 생성 잠김 |
| 6 | 생성 후 | 만든 파일을 다시 읽어 시트명·행 수·합계 확인 | error |

- 거래처가 하나인 부서는 배분이 자동이라 5번이 항상 성립하고, 4번이 곧 "견적 ↔ 정산" 검증이 된다.
  실제 샘플에서 바둑(444,000)·주산암산(68,000)이 정확히 맞았다.
- 비교 기준은 견적서에 적힌 **합계금액(공급가액+세액)** 이 기본값이고, 견적서마다 바꿀 수 있다.
- **프로그램은 어떤 원본 값도 바꾸지 않는다.** 사용자가 셀을 고치면 `raw_*` 에 원문이 남고 `edited` 로 표시된다.

## 10. 에듀파인 XLSX 생성

실물 샘플에서 확인한 사양(02 문서 5장)을 그대로 재현한다.

| 항목 | 값 |
|---|---|
| 시트 | `품목내역` 하나. 상수 한 곳에만 둔다 |
| 머리글 | 1행, `내용` `규격` `수량` `예상단가` |
| 자료 | 2행부터 연속. 빈 행·합계 행 **없음** |
| 자료형 | `내용`·`규격` 문자, `수량`·`예상단가` **숫자**(`#,##0`) |
| 값 | `규격`=`식`, `수량`=`1`, `예상단가`=그 재원 금액 |
| 서식 | 머리글 **검정 바탕 + 흰 굵은 글씨(Dotum 9) + 빨강 가는 테두리**(첫 칸만 왼쪽 선 있음), 본문 Dotum 9·자동색 가는 테두리·세로 가운데·줄바꿈 |
| 열 너비 | A 44.5 / B~D 12.25 (아래 주의 참고) |
| 병합·숨김·수식 | 없음 |

> ### 에듀파인 업로드 검증 완료 (2026-09-13)
>
> 이 사양으로 만든 파일을 사용자가 **실제 에듀파인에 올려 정상 업로드되는 것을 확인했다.**
> P0·P1 내내 "생성한 XLSX 를 에듀파인이 받아 주는가" 가 마지막 불확실성이었는데 **해소됐다.**
> 아래 사양은 이제 추정이 아니라 **실제 업로드로 확인된 규격**이다.

> **"서식까지 똑같이" 의 뜻**: XML 이 같다는 뜻이 아니다(다른 생성기로는 불가능하다).
> **화면에 보이는 값과 서식이 같다**는 뜻이고, 검증은 색을 RGB 로 정규화해 비교한다.
> **열 너비만 예외다** — `rust_xlsxwriter` 는 문자너비를 픽셀로 바꿨다 되돌려 저장값이 양자화되므로
> 44.5·12.25 에 **도달할 수 없다**(80~330픽셀 전수 확인). 가장 가까운 값(311·86픽셀)을 쓰고 차이는 0.04~0.07 문자다.

- `rust_xlsxwriter` 로 만든다. 재원마다 파일 하나. **예상단가가 0인 행은 만들지 않는다.**
- **행이 하나도 없는 재원은 파일을 만들지 않는다**(14장 14번). 결과 화면에
  `자유수강권: 대상 금액 없음 · 파일 생성 안 함` 으로 표시한다. "빈 파일도 만들기" 옵션은 없다.
- 저장: 임시 파일 → calamine 으로 다시 열어 검증 → 사용자가 고른 폴더로 이동. 같은 이름이 있으면 덮어쓸지 묻는다.
- 마지막 저장 폴더를 기억한다. 폴더가 사라졌으면 `문서` 로 되돌린다.
- 행 순서는 부서 설정의 등록 순서(사용자가 끌어 정렬)를 기본값으로 한다.

## 14. 승인된 결정

사용자가 명시적으로 확정한 것만 적는다. (2026-09-13)

1. **견적서 파일명 규칙** (2026-09-13 보완). 정확한 원칙은 이것이다 —
   **"견적서 파일명에는 최소한 부서명을 반드시 포함한다.
   거래처가 여러 개인 부서는 거래처 관리명까지 넣는 것을 정상 운영 규칙으로 한다."**
   - **파일명 형식을 강제하지 않는다.** `주산암산부 견적서.jpg` · `주산암산 견적서.jpg` ·
     `주산암산 견적서류.jpg` · `주산암산 9월 견적서.jpg` 는 모두 맞는 이름이고 똑같이 매칭된다.
     `부`·`견적서`·`견적서류`·월 표시 같은 주변 글자는 매칭에 영향을 주지 않는다.
   - 자동 매칭은 **등록된 부서명 또는 거래처 관리명이 파일명에 들어 있는지**로만 판단한다.
   - 거래처가 하나인 부서는 부서명만 있어도 **자동 매칭**한다.
   - 거래처가 여럿인 부서에 부서명만 있으면 **추측하지 않는다.**
     "로봇과학 부서는 거래처가 여러 개입니다" 라고 표시하고 사용자가 관리명을 고르게 한다.
   - 우선순위: ① 거래처 관리명 포함 검사 ② 품의 부서명 포함 검사 ③ 거래처 1개면 자동
     ④ 2개 이상이면 후보 표시 후 선택 ⑤ 부서명도 못 찾으면 수동 선택.
   - **정산 별칭은 파일명 매칭에 쓰지 않는다. 숫자 접미사를 떼거나 붙여 거래처를 추정하지 않는다.**
2. **견적서 품목명은 원문 그대로 쓴다.** 과거 사람이 `바둑교재(상상바둑)` → `바둑교재` 로 줄인 사례가 있어도
   프로그램은 따라 하지 않는다. **자동 축약·가공을 하지 않는다.** 최종 내용 문구를 사용자가 직접 고치는 기능은 유지한다.
   (2026-09-13 보완 → 아래 12번에서 원문과 품의 표시명을 나눈다.)
3. **정산자료 이름의 숫자 접미사는 거래처 구분이 아니다.** `토탈공예미니어처1·2` 같은 이름은 원자료에서
   강좌 등이 나뉜 것일 뿐이고 실제 품의에서는 `토탈공예미니어처부` 하나로 합쳐진다.
   우리가 정의한 거래처 관리명(`로봇과학1`·`로봇과학2`)과 **절대 같은 개념으로 취급하지 않는다.**
4. **정산자료 여러 행 → 한 품의 부서 매핑을 부서 설정에서 관리한다.** 같은 부서로 매핑된 행들의
   재원별 금액은 **자동 합산**한다. (예: 토탈공예미니어처 115,000 + ~1 460,000 + ~2 115,000 → 수익자 690,000)
5. **한 품의 부서가 여러 거래처를 쓰면 견적서마다 별도의 품의 항목이 된다.** 정산자료에 부서 하나로
   합쳐져 있어도 **견적 금액 비율 등으로 자동 배분하지 않는다.** 사용자가 거래처별 재원 금액을 직접 입력한다.
6. **배분은 총액이 아니라 재원 4개를 각각 입력한다.** 검증은 두 방향이다.
   **세로** — 거래처별 같은 재원의 합 == 정산자료의 그 재원 금액(4개 각각).
   **가로** — 한 거래처의 재원 4개 합 == 그 거래처 견적서 총액.
   모든 세로 합과 가로 합이 맞아야 정상이다. **프로그램은 금액을 추정하거나 자동 보정하지 않는다.**
7. **정산자료 이름과 거래처 관리명을 문자열 규칙으로 억지로 연결하지 않는다.** 특히 숫자 접미사를 보고
   거래처라고 판단하지 않는다. 부서 설정에서 다음 개념을 분리해 관리한다 —
   품의 부서 · 품의 표기명 · 정산자료 별칭 · 거래처 관리 단위 · 거래처 관리명 · 거래처명(선택).
8. **기존 샘플 파일의 이름은 운영 파일명 규칙의 정답이 아니다.** 샘플의 목적은 문서 구조와 파싱 검증이다.
   (`로봇과학 견적서.hwp` 에 숫자가 없는 것은 샘플을 만들 때 규칙을 적용하지 않았기 때문이다.)
9. **견적서의 행 종류와 할인 처리** — 기존 C2 에 대한 확정.
   - **배송비·택배비**: 현재 업무에서 쓰는 견적서에는 없다. **지금은 별도 자동 처리 규칙을 만들지 않는다.**
     나중에 실제 견적서에서 발견되면 그때 규칙을 추가한다.
   - **할인**: 견적서에 할인 금액이 있으면 **반드시 읽어 온다.** 실제 구매 품목이 아니므로 **`N종` 계산에는 넣지 않고**
     대표품목 후보도 아니다. **견적 총액에는 반영한다.**
     예) 교재A 100,000 · 교재B 200,000 · 할인 -30,000 → 품목수 2종, 문구 `○○부 교재A 외 1종`, 견적 총액 270,000.
   - **할인 금액은 견적서 원문 값을 그대로 쓴다.** 할인율·할인액을 추정하거나 자동 계산하지 않는다.
     `할인 30,000` · `할인금액 30,000` · `DC -30,000` 처럼 표기가 다를 수 있으므로,
     파서는 **① 할인 행임을 먼저 판별하고 ② 총액에 어떤 부호로 반영되는지 확인할 수 있게** 만든다.
     **자동으로 부호를 바꾸어 원본 값을 수정하지 않는다.**
   - **행 분류를 네 종류로 한다**: `일반 품목` · `할인/금액 조정` · `합계/소계` · `빈 행`.
     "이름이 있고 금액이 0보다 큰 행만 품목" 규칙만으로 할인 행을 처리하지 않는다.
     `할인/금액 조정` 행은 **N종 제외 · 대표품목 후보 아님 · 견적 총액 검증에는 포함 · 원문과 금액 보존**.
   - **사은품**: → 아래 10번에서 확정.
10. **금액 0원 행(사은품 포함)** — 기존 `C2'` 에 대한 확정.
    견적서에 사은품이 있어도 **금액이 0원이면 실제 품의 금액에 영향을 주지 않는 품목**이다. 따라서
    **품의 대상 품목에서 제외 · `N종` 계산에서 제외 · 대표품목 후보에서 제외 · 견적 총액에 영향 없음.**
    다만 **원문에 존재하므로 완전히 지우지 않고 추출 결과 화면에 참고용으로 보여 준다.**
    예) 교재A 100,000 · 교재B 200,000 · 사은품 노트 0 → 품목수 2종, 문구 `○○부 교재A 외 1종`, 품목 금액 300,000.
    **사은품 여부와 관계없이 금액이 0원인 행은 품목 수 계산에서 기본적으로 제외한다.**
    (그러므로 판별 기준은 `사은품` 이라는 낱말이 아니라 **금액이 0인지**다.)
    **원본 데이터 자체를 삭제하거나 수정하지 않는다.**
11. **품의 표기명은 모든 부서에 붙인다** — 기존 `C3` 에 대한 확정.
    기존 실제 품의서의 `드론항공과학교구세트 1종` 처럼 부서 접두가 빠진 것은 **앞으로 쓸 정상 규칙으로 보지 않는다.**
    항공드론도 다른 부서와 같이 품의 표기명을 붙인다 —
    품의 부서 `항공드론` · 품의 표기명 `항공드론부` · 품목명 `드론항공과학교구세트` ·
    품의 표시용 `드론항공과학 교구세트` → 최종 문구 **`항공드론부 드론항공과학 교구세트 1종`**.
    따라서 **부서별 "접두 없음" 옵션은 만들지 않는다.**
12. **품목명은 원문과 품의 표시명을 나눈다** — 2번의 보완.
    `raw_name` = 견적서 원문(절대 안 바뀜), `display_name` = 품의에 쓸 현재 값. **기본값은 `display_name = raw_name`.**
    **프로그램이 임의로 띄어쓰기·축약·맞춤법 교정을 하지 않는다.** 사용자가 추출 결과 화면에서 고친 경우에만 달라진다.
    고치면 원문은 그대로 보존되고 수정된 표시명이 문구 생성에 쓰인다.
    - 바둑은 손대지 않으면 기본 자동 결과가 계속 `바둑부 바둑교재(상상바둑) 1종` 이다.
    - 항공드론은 사용자가 표시명을 `드론항공과학 교구세트` 로 고치면 `항공드론부 드론항공과학 교구세트 1종` 이 된다.
13. **금액 불일치 처리.**
    - 세로 또는 가로 금액 검증에서 불일치가 있으면 **기본적으로 Excel 생성을 차단한다.**
    - **프로그램이 금액을 자동 수정하거나 보정하지 않는다.**
    - 다만 실제 업무상 의도된 차이일 수 있으므로, 사용자가 그 오류를 **직접 확인하고 사유를 입력하면** 생성할 수 있다.
    - **확인 사유는 공란을 허용하지 않는다.**
    - 확인 여부와 사유는 **해당 작업 데이터에 보존한다.**
    - **생성되는 에듀파인 XLSX 에는 확인 사유를 넣지 않는다.**
    - 전체 오류를 무조건 허용하는 **"항상 허용" 설정은 만들지 않는다.**
14. **0원 재원 파일은 항상 만들지 않는다.**
    - 수익자·초과금·지원금·자유수강권 중 **해당 재원의 최종 품의 행이 하나도 없으면 그 XLSX 를 생성하지 않는다.**
    - 결과 화면에 `자유수강권: 대상 금액 없음 · 파일 생성 안 함` 처럼 명확히 표시한다.
    - **"빈 파일도 만들기" 같은 별도 옵션은 만들지 않는다.**
15. **월별 작업 데이터를 보존한다.** 작업마다 아래를 남긴다.
    등록한 견적서 정보 · 견적서 추출 결과 · **raw 값** · 사용자가 고친 `display_name` 및 기타 수정값 ·
    대표품목 선택 · 최종 내용 문구 수정값 · 정산자료 원문과 부서 매칭 결과 · 거래처별 재원 배분값 ·
    검증 결과 · 사용자가 확인한 불일치와 확인 사유 · 생성 파일 기록.
    - **프로그램을 껐다 켜도 작업을 골라 이어서 진행할 수 있어야 한다.**
    - 원본 견적서 파일 자체는 DB 에 복사하지 않고 **경로·크기·해시만** 저장한다.
    - **원본 파일이 옮겨지거나 지워져도 이미 추출해 저장한 작업 데이터는 유지한다.**

### 16번. 사진에서 깨져 읽힌 합계 (2026-09-13 승인)

`₩68,000` 이 `鬧8,000` 처럼 숫자에 비정상 문자가 섞여 표기 합계를 믿을 수 없을 때.

- 프로그램이 **추정하거나 보정하지 않는다.**
- 그 표기 합계는 **읽지 못함/신뢰 불가**로 다룬다.
- **OCR 원문을 보존하고** 화면에서 사용자가 볼 수 있게 한다.
- 비교 기준은 **정상적으로 뽑힌 품목들의 금액 합**을 쓴다.
- 상태는 **확인 필요**로 표시한다.
- **단, 품목 합 자체도 검증되지 않으면 정상으로 취급하지 않는다**(인식 불확실).
- 이 규칙은 **OCR 경로에만** 적용한다. XLSX·HWP 등 구조화된 문서의 기존 규칙은 그대로다.

### 17번. OCR 의 목표 수준 (2026-09-13 승인)

100% 무인 자동 처리가 아니다. **사람의 최종 확인을 전제로 한 보조 자동화**다.
품목 일부를 잘못 읽었다고 전체를 실패로 처리하지 않는다.
정확도를 위해 외부 AI API 나 새 대형 의존성을 추가하지 않는다.
