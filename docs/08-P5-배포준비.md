## 1. 이름

| 자리 | 값 | 왜 |
|---|---|---|
| 사용자에게 보이는 이름 | **방과후 품의 도우미** | 창 제목 · 시작 메뉴 · 프로그램 추가/제거 · 설치 프로그램 · 화면 좌측 제목 |
| 영문 내부 이름 | **afterschool-purchase-helper** | 실행 파일 · npm 패키지 · Rust crate |
| Rust 라이브러리 | `afterschool_purchase_helper_lib` | Rust 식별자라 밑줄 |
| bundle identifier | **`kr.school.afterschool-purchase-helper`** | 자료 폴더 이름이 된다. **한 번 정하면 바꾸지 않는다** |
| GitHub 저장소 | `AfterSchool-Purchase-Helper` (**Private**) | 계정 `lohemal`. 아직 만들지 않음 |
| 버전 | **0.1.0** | 세 곳이 같다 (`npm run check:version`) |

**한글 이름을 쓰되 파일 이름은 영문으로 간다.** Tauri 는 설치 파일 이름을 `productName` 에서 만들기 때문에
실제로 만들어지는 파일은 `방과후 품의 도우미_0.1.0_x64-setup.exe` 다.
GitHub 릴리스는 첨부 파일 이름에서 한글을 떼어 내므로, 릴리스 워크플로가
**영문 이름으로 복사한 뒤** 올리고 `latest.json` 도 그 이름을 가리킨다.
이것을 빠뜨리면 업데이터가 파일을 못 찾아 **조용히 깨진다**(다른 프로젝트에서 겪은 일).

`quotemgr` 라는 예전 이름이 일부러 남아 있는 자리가 둘 있다.

- `datadir.rs` 의 `LEGACY` — 예전 자료를 찾아오는 데 쓴다.
- `setup.rs` 의 `quotemgr-setup-v1` — 설정 내보내기 파일의 형식 표시. 바꾸면 예전에 내보낸 파일을 못 읽는다.

## 2. 자료를 두는 자리

```
%APPDATA%\kr.school.afterschool-purchase-helper\purchase-helper.db
```

프로그램이 설치된 곳(`%LOCALAPPDATA%\방과후 품의 도우미`)이 **아니다.**
그래서 새 버전으로 올려도, 지웠다 다시 깔아도 작업이 그대로다.

### 예전 자료를 잃지 않는다

P5 에서 이름이 바뀌며 자료 폴더 이름도 바뀌었다. 개발판으로 실사용 시험을 하며 만들어 둔 작업이
사라진 것처럼 보이면 안 되므로, **처음 한 번** 예전 자리에서 가져온다(`src-tauri/src/datadir.rs`).

- 새 자리에 자료가 있으면 **건드리지 않는다.**
- **예전 자료를 지우지 않는다.** 복사만 한다.
- 파일을 그대로 복사하지 않고 **SQLite 가 스스로 복사**하게 한다(`backup`).
  그래야 아직 반영되지 않은 WAL 까지 온전히 따라온다. (실제로 3.2MB WAL 이 있었다.)
- 옮기다 실패해도 프로그램은 새 자료로 그냥 시작한다.

시험 4건이 이를 고정한다(가져오기 · 덮어쓰지 않기 · 없을 때 · 깨졌을 때).

### 실제로 확인한 것

설치본을 처음 켠 직후 새 자리에 자료가 생겼고, 안에는 개발판에서 하던 작업이 그대로 있었다.

```
스키마 v2
작업 1 · 부서 17 · 견적서 3 · 품목 7
작업: 2026학년도 9월 교재비 · 9월 · 교재비
```

### 지울 때

프로그램을 제거해도 **이 폴더는 지워지지 않는다.** 실제로 확인했다(8장).
정말 지우려면 사용자가 위 폴더를 직접 지워야 한다.
**설치·업데이트·제거 어느 쪽도 사용자 자료를 자동으로 지우지 않는다.**

## 3. 만든 품의 파일이 가는 곳

사용자가 고른 폴더에 저장하고 그 자리를 기억한다(`setting` 표의 `last_output_dir`).
다음에 만들 때 같은 폴더가 미리 채워져 있다. 앱 내부 경로나 임시 폴더에 숨지 않는다.

- 생성 화면에서 **[폴더 고르기]** 로 고른다.
- 만든 뒤 화면에 **만든 파일의 전체 경로**가 나오고 **[폴더 열기]** 로 탐색기에서 열 수 있다.
- 같은 이름이 이미 있으면 덮어쓰지 않고 `… (2).xlsx` 로 비켜 만든다(P4).

이미 되던 기능이라 새로 만들지 않았다.

## 4. 설치 파일

| | |
|---|---|
| 만든 것 | `방과후 품의 도우미_0.1.0_x64-setup.exe` |
| 크기 | 3,485,780 bytes (약 3.3 MB) |
| SHA-256 | `aa368ae489dedf95202e80ee3a9a7de2eb57e801c185ff14128097002adb4ace` |
| 서명 | `방과후 품의 도우미_0.1.0_x64-setup.exe.sig` (444 bytes) |
| 릴리스에 올릴 이름 | `afterschool-purchase-helper_0.1.0_x64-setup.exe` |
| 설치 방식 | NSIS · `currentUser` (관리자 권한 필요 없음) |

### 빌드하다 만난 함정

서명 키를 `TAURI_SIGNING_PRIVATE_KEY_PATH` 로 넘겼더니 빌드가 **성공(exit 0)했는데 `.sig` 만 없었다.**
`TAURI_SIGNING_PRIVATE_KEY` 에 **키 파일의 내용**을 넣어야 한다.
릴리스 워크플로가 `.sig` 가 없으면 멈추도록 되어 있는 이유가 이것이다.

## 5. 업데이트

| | |
|---|---|
| 방식 | Tauri updater · GitHub Release 기반 |
| 확인하는 곳 | `https://github.com/lohemal/AfterSchool-Purchase-Helper/releases/latest/download/latest.json` |
| 설치 방식 | `passive` (설치 창이 뜨지만 사용자가 누를 것이 없다) |
| 산출물 | `createUpdaterArtifacts: true` → `.sig` 를 함께 만든다 |

### 언제 확인하나

프로그램이 **켜진 뒤 3초 뒤에** 한 번, 조용히 확인한다(`src/components/UpdateBanner.tsx`).

- 시작을 막지 않는다.
- 새 버전이 없으면 **아무것도 보여 주지 않는다.**
- 인터넷이 없거나 확인에 실패하면 **아무 말 없이 넘어간다.** 품의 작성과 상관없는 일이다.
- 찾아도 **사람이 [지금 업데이트] 를 눌러야** 설치한다. 작업 도중 갑자기 닫히면 안 된다.

### `relaunch()` 를 부르지 않는다

Windows 에서 `install()` 은 돌아오지 않는다. 설치 프로그램을 띄우고 앱을 스스로 끝내며,
설치가 끝나면 NSIS 가 앱을 다시 켠다. 여기서 `relaunch()` 를 부르면 방금 뜬 설치 프로그램과 경쟁해
앱이 먼저 켜지는 바람에 파일을 바꾸지 못하고 **구 버전 그대로 남는다.**

**2026-09-14 — 비밀번호 있는 새 키로 교체했다.**

| | |
|---|---|
| 비밀번호 | 같은 폴더의 `PASSWORD.txt` (28자, 무작위로 생성) |
| 확인 | 빈 비밀번호로 서명하면 `Wrong password` 로 **막힌다.** 올바른 비밀번호로는 서명된다 |

> 키 파일과 비밀번호는 **저장소에 넣지 않는다.** `.gitignore` 가 `*.key` 를 막지만
> 애초에 프로젝트 폴더 밖에 둔다.
> **이 세 파일을 잃어버리면 자동 업데이트를 되살릴 수 없다.** 다른 곳에 한 벌 더 보관할 것.
> 공개 릴리스를 한 뒤에는 키를 바꿀 수 없다 — 쓰던 사람들이 손으로 다시 설치해야 한다.

## 10. Git 제외 정책

`.gitignore` 를 공개 저장소 기준으로 다시 썼다. 형식만 보고도 막는다.

```
test/fixtures-local/   실제 업무 샘플
test/out/              시험 산출물
*.db *.sqlite          사용자 자료
*.xlsx *.xls *.xlsm    만든 품의 파일 · 견적서
*.hwp *.hwpx *.pdf *.jpg *.jpeg   견적서로 올 수 있는 형식
*.key *.pem *.pfx *.crt .env      서명 키 · 비밀 정보
node_modules/ target/ dist/ src-tauri/gen/ release/
```

앱 아이콘은 `!src-tauri/icons/**/*.png` 로 풀어 준다.

**`.gitignore` 만 믿지 않는다.** `git init` 뒤에 `git ls-files` 로 실제 추적 대상을 다시 검사한다
(`npm run check:public`).

### 실제 샘플이 없어도 시험이 돈다

공개 저장소를 내려받으면 `test/fixtures-local/` 이 없다. 확인했다.

```
cargo test --lib        163건 통과 (샘플 없이)
npm run check:model     통과
npm run build           통과
```

실제 샘플이 필요한 시험 14건은 `#[ignore]` 이고, 돌려도 **왜 건너뛰는지 말하고** 끝난다.

```
건너뜀 — 이 시험에는 로컬 전용 샘플이 필요합니다: test/fixtures-local/바둑 견적서.xlsx
(실제 업무 자료라 저장소에 넣지 않습니다. 자세한 내용은 docs/08-P5-배포준비.md)
```

## 14. GitHub 저장소 — **아직 만들지 못했다**

이 컴퓨터에 **저장소를 만들 수단이 없다.**

| 확인한 것 | 결과 |
|---|---|
| `gh` CLI | **없음** |
| `GITHUB_TOKEN` · `GH_TOKEN` 환경변수 | 없음 |
| Git Credential Manager | 있음 (`git push` 용 자격증명 1건 저장됨) |
| `git ls-remote origin` | `Repository not found` — 저장소가 없다 |

저장된 자격증명은 **push 할 때 쓰는 것**이라 저장소를 새로 만들지는 못한다.

### 준비해 둔 것

```
로컬 저장소   초기화 완료, 브랜치 main, 첫 커밋 완료
remote        origin → https://lohemal@github.com/lohemal/AfterSchool-Purchase-Helper.git
커밋 작성자   lohemal <lohemal@users.noreply.github.com>  (다른 저장소와 같다)
```

저장소만 만들어지면 `git push -u origin main` 한 번으로 끝난다.

### 사용자가 할 일

1. https://github.com/new 에서 만든다.
   - Owner `lohemal` · Repository name `AfterSchool-Purchase-Helper`
   - **Private**
   - **README · .gitignore · license 를 넣지 않는다** (넣으면 로컬과 부딪힌다)
2. 만든 뒤 이 폴더에서 `git push -u origin main`

## 15. 최초 Release 는 업데이터를 끝까지 시험할 수 없다

v0.1.0 은 업데이터의 **기준점**이다. 여기서 올라갈 더 높은 버전이 아직 없으므로
"새 버전을 찾아 내려받아 설치한다" 를 실제로 해 볼 수는 없다.

대신 지금 확인한 것은 이렇다.

| 확인한 것 | 결과 |
|---|---|
| 서명이 앱의 공개 키와 짝인가 | **통과** — ed25519(prehashed) 로 실제 검증했다 (`npm run check:release`) |
| 설치 파일 이름과 `latest.json` 의 url 이 같은가 | 같다 |
| `latest.json` 에 BOM 이 없는가 | 없다 |
| 버전이 세 곳과 `latest.json` 에서 같은가 | 모두 0.1.0 |
| endpoint 가 이 저장소를 가리키는가 | 그렇다 |

**업데이트가 실제로 되는지는 다음 버전(v0.1.1 등)을 낼 때 확인한다.**
시험만을 위한 의미 없는 릴리스는 만들지 않는다.

확인할 때 볼 것: 앱을 켜고 3초 뒤 알림이 뜨는가 → `[지금 업데이트]` → 내려받기 →
설치 프로그램이 앱을 끄고 설치 → 앱이 다시 켜짐 → 버전이 올라갔는가 → **작업이 그대로인가.**

```
TAURI_SIGNING_PRIVATE_KEY 에 키 파일의 **내용**이 들어갔는지 확인하세요.

```

워크플로는 이 단계에서 멈추고, 그 뒤 `npm run check:release` 가 서명을 실제로 검증한다.
**서명 없이 릴리스가 만들어질 수 없다.**

## 17. 서명 키를 다시 만들었다 (2026-09-14)

최초 Release 전에 **서명 키 구조를 깨끗하게** 정리했다. Release 가 아직 하나도 없어
지금 바꾸면 아무 손해가 없기 때문이다.

### 왜 다시 만들었나 — BOM 한 글자

비밀번호 파일을 PowerShell 5.1 의 `Set-Content -Encoding utf8` 로 만들었는데,
**이 옵션은 파일 앞에 BOM(`EF BB BF`)을 붙인다.**

- 키를 만들 때는 bash 의 `cat` 으로 읽었다 → BOM 까지 비밀번호에 들어갔다.
- 사람이 `Get-Content -Raw` 로 복사하면 PowerShell 이 BOM 을 떼어 낸다 → 값이 달라진다.

그래서 CI 가 `incorrect updater private key password: Wrong password for that key` 로 막혔다.
로컬 빌드는 계속 `cat` 을 썼기 때문에 멀쩡히 되어, 문제가 늦게 드러났다.

| 실행 | 오류 | 뜻 |
|---|---|---|
| run #1 | `Invalid symbol 45, offset 3` | secret 이 base64 가 아님 |
| run #2 | `Invalid symbol 36, offset 0` | secret 이 `$` 로 시작 (경로를 넣음) |
| run #3 | `Wrong password for that key` | **키는 맞고 비밀번호가 BOM 때문에 어긋남** |

### 새 키

| | |
|---|---|
| 비밀번호 | 영문·숫자 **32자**. BOM·줄바꿈·앞뒤 공백 **없음** (바이트로 확인) |
| 만든 방법 | PowerShell 을 거치지 않고 Node 로 바이트를 직접 썼다 |
| 개인 키 | `%USERPROFILE%\.afterschool-purchase-helper-release\` (저장소 밖) |
| 폐기한 키 | 같은 폴더의 `폐기-임시키-…` · `폐기-BOM비밀번호키-…` 로 분리. 그 키로 만든 산출물은 모두 지웠다 |

### 만든 직후 네 가지를 실제로 검증했다

| | 결과 |
|---|---|
| A. 올바른 비밀번호로 서명 | **성공** |
| B. 빈 비밀번호 | `Wrong password` — 실패해야 정상 |
| C. 다른 비밀번호 | `Wrong password` — 실패해야 정상 |
| D. 새 공개 키로 서명 검증 | **통과**. 폐기한 키와 키 ID 가 다름도 확인 |

### 신뢰 사슬을 눈으로 확인했다

새 공개 키가 **빌드된 실행 파일 안에 실제로 들어 있는지** 바이트로 찾아봤다.

```
새 공개 키 있음   : 예
폐기 BOM 키 있음  : 아니오
폐기 임시 키 있음 : 아니오
tauri.conf.json 과 같은가 : 예
```

이것이 중요한 이유는, 앞으로 나올 v0.1.1 을 **이 v0.1.0 앱이 검증**하기 때문이다.
앱 안의 공개 키와 CI 가 서명할 개인 키가 한 쌍이어야 업데이트가 된다.

### 같은 실수를 막는 장치

키 폴더에 `secret-확인.mjs` 를 두었다. 클립보드에 복사한 값을 **파일과 바이트 단위로** 맞춰 보고
맞는지만 알려 준다. 값은 화면에 보여 주지 않는다.

```
node "%USERPROFILE%\.afterschool-purchase-helper-release\secret-확인.mjs" key
node "%USERPROFILE%\.afterschool-purchase-helper-release\secret-확인.mjs" password
```

같은 폴더 `README.txt` 에 이번에 겪은 함정 세 가지를 적어 두었다
(경로를 넣는 실수 · BOM · `TAURI_SIGNING_PRIVATE_KEY_PATH` 로 주면 서명만 조용히 빠지는 것).

### v0.1.0 태그를 다시 만든 것에 대해

Release 가 한 번도 만들어지지 않았고 기존 태그로 돌린 워크플로는 모두 실패했으므로,
**이번 한 번만** 사용자 승인을 받아 태그를 새 커밋으로 옮겼다.
**v0.1.0 Release 가 성공한 뒤부터는 배포된 태그를 옮기거나 다시 쓰지 않는다.**
