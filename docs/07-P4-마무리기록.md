# P4 마무리 기록 — 실제로 쓸 수 있는 물건으로 다듬기

작성: 2026-09-13
기준 문서: `docs/01-설계안.md` · `06-P2-P3-진행기록.md`

> **한 줄 요약** — 새 업무 기능은 더하지 않았다.
> 잘못 읽힌 줄을 **눈에 띄게** 하고, 원본을 화면에서 바로 보게 하고,
> 실패했을 때 **다음에 뭘 해야 하는지** 말해 주고, 키보드로 이어서 고칠 수 있게 했다.
> 그러다 **한글 프로세스가 새는 실제 결함**을 찾아 고쳤다.

---

## 1. P4-1 추출 검토 사용성

### 고친 것

**프로그램이 이미 계산해 둔 신뢰도를 화면이 쓰지 않고 있었다.** 줄마다 `confidence` 와 경고를
만들어 DB 에 넣어 두고도 표에는 아무 표시가 없었다. 사람이 열 줄을 하나하나 원본과 대조해야 했다.

| 무엇 | 어떻게 |
|---|---|
| 다시 볼 줄 | 줄 전체를 **노란 배경 + 왼쪽 세로 막대**로 표시한다 |
| 왜 다시 봐야 하는지 | 물품명 아래에 **프로그램이 만든 경고 문장 그대로** 한 줄 |
| 몇 줄이나 되는지 | 표 제목 아래 "노란 줄 N개를 원본과 맞춰 봐 주세요" |
| 견적서 고르기 목록 | 견적서마다 "확인할 줄 N개" 와 신뢰 상태 배지 |
| 빈 줄 | "비어 있는 줄이 N개 있습니다 — 빈 줄도 「N종」에 들어갑니다" |

판단 규칙은 `src/lib/itemStatus.ts` 한곳에 있고 `scripts/check-review.ts` 가 지킨다.
**화면이 스스로 판단하지 않는다.** 경고 문장이 있으면 그 문장을 그대로 쓰고, 없이 신뢰도만 낮으면
까닭을 한 줄로 적는다.

### 삭제는 그대로 한 번 누르기

잘못 읽힌 줄을 지우는 일이 번거로운지 살폈다. 지금도 **단추 한 번**이고 확인 창이 없다.
확인 창을 넣으면 오히려 번거로워지므로 넣지 않았다.
잘못 지웠으면 `원본에서 다시 읽기` 로 처음 상태로 되돌릴 수 있다.
**일괄 삭제 같은 새 기능은 만들지 않았다** — 실사용에서 필요하다는 말이 나오면 그때 넣는다.

## 2. P4-2 원본 확인

매번 탐색기에서 파일을 다시 찾지 않도록 검토 화면에 단추 셋을 두었다.

| 단추 | 하는 일 |
|---|---|
| **원본 보기** | 사진·스캔 PDF 의 **원본 그림을 화면 안에** 펼친다 (쪽마다 `1쪽`·`2쪽` 딱지) |
| **원본 파일 열기** | 이 컴퓨터의 기본 프로그램으로 원본을 연다 (엑셀·한글·PDF 뷰어) |
| **원본에서 다시 읽기** | 지금까지 고친 것을 버리고 원본을 다시 읽는다 |

- 그림은 **눌렀을 때만** 받아 온다. 한 장이 수백 KB 라 늘 들고 있지 않는다.
- 화면에 보낼 때 한 변 1600픽셀로 줄인다. **원본 파일은 손대지 않는다.**
- XLSX·HWP·글자 PDF 는 보여 줄 그림이 없다. 대신 품목의 `원본 위치`(`견적서!C12` · `1쪽`)를
  쓰고 `원본 파일 열기` 로 넘긴다.

### PDF 렌더러는 넣지 않았다

글자 PDF 를 그림으로 그리려면 pdfium 같은 **6MB 짜리 이진 파일**을 배포판에 넣어야 한다.
학교 PC 에 배포하는 물건이라 임의로 넣지 않았다(설계안 6장 결정). 스캔 PDF 는 P3 이 이미 쪽마다
그림을 꺼내고 있으므로 **렌더러 없이** 그대로 보여 준다. 글자 PDF 는 `원본 파일 열기` 로 충분하다.
필요하다고 판단되면 그때 의논해서 넣는다.

## 3. P4-3 실패했을 때 하는 말

### 원칙

1. 기술 오류 문자열을 그대로 보여 주지 않는다. 자세한 원인은 `AppError::detail` 에만 담는다.
2. 모든 안내는 **다음에 무엇을 할지**로 끝난다.
3. OCR 실패는 프로그램 오류와 구분해서 말한다.

## 4. P4-4 키보드

| 키 | 하는 일 |
|---|---|
| `Tab` · `Shift+Tab` | 옆 칸 (브라우저 기본 그대로) |
| `Enter` | 값을 확정하고 **같은 칸의 다음 줄**로 내려간다 |
| `Shift+Enter` | 윗줄 같은 칸으로 |
| `Esc` | **저장하지 않고** 고치기 전 값으로 되돌린다 |
| 품목 줄 추가 | 새 줄의 물품명 칸으로 초점이 바로 간다 |

한 줄에는 글자 칸이 늘 다섯(물품명·규격·수량·단가·금액)이므로 다음 줄 같은 칸은 다섯 칸 뒤다
(`src/lib/gridKeys.ts`).

### 한글 입력은 건드리지 않았다

- 조합 중(`isComposing`)에는 **어떤 키도 가로채지 않는다.** Enter 는 한자 변환, Esc 는 조합 취소에
  IME 가 쓴다. 이 규칙이 없으면 P1 에서 고친 버그가 되살아난다.
- `Esc` 는 상태 기계에 `cancel` 로 들어가고, 조합 중이면 아무것도 하지 않는다.
- `scripts/check-ime.ts` 에 Esc 시험 셋을 더했다. 조합 중 Esc, Esc 뒤 blur 에 저장이 없는지까지 본다.

### 배분 화면의 금액 칸

`value={comma(...)}` 를 매 타건마다 다시 써 넣고 있었다. 그래서 쉼표가 끼어들 때마다
**글자 자리(캐럿)가 끝으로 튀어** 가운데 숫자를 고칠 수 없었다.
공통 `TextField` 로 바꾸고, 합계는 `onDraftChange` 로 따라가게 했다.

### 브라우저 확인

순수 함수 시험이 못 보는 부분(초점 이동·Esc·자동 초점)은 `test/ui/keys.html` 로 실제 브라우저에서 확인했다.
2026-09-13 확인: Enter `1-qty → 2-qty`, Shift+Enter `2-qty → 1-qty`,
Esc 뒤 초점을 잃어도 **저장이 한 건도 일어나지 않았다**, 새 줄 자동 초점 정상.

## 5. P4-5 파일·자료 안전

| 항목 | 결과 |
|---|---|
| 원본 파일 수정 금지 | **시험으로 고정.** `originals_are_never_modified` 가 `fixtures-local` 의 파일 5개를 견적서·정산자료·원본보기로 모두 읽은 뒤 SHA-256 이 같은지 본다 |
| HWP 임시 파일 | 변환이 끝나면 `in-*.hwp` · `out-*.hwpx` 를 지운다 |
| OCR 임시 이미지 | **파일로 쓰지 않는다.** 3배 확대본은 메모리에만 있다 |
| 원본 보기 임시 파일 | 없다. 메모리에서 바로 화면으로 보낸다 |
| 비정상 종료 뒤 남은 임시 파일 | **시작할 때 한 번 치운다** (`tempclean.rs`). 우리가 만든 `%TEMP%/quotemgr-*` 안만, **하루 지난 것만** 지운다 |
| DB 저장 안정성 | WAL · `foreign_keys=ON` · `synchronous=NORMAL` · 5초 대기. 모든 쓰기가 트랜잭션이고 오류면 통째로 되돌린다 |
| 작업 이어하기 | `p4_full_end_to_end` 가 **DB 를 닫았다 다시 열어** 작업·견적서·품목·확인 사유·만든 파일이 그대로인지 본다 |
| 원본 파일 이동·삭제 | 등록해 둔 내용은 그대로 쓴다. 화면에 "원본 파일이 있던 자리에 없습니다" 라고 알리고 다시 읽기 단추는 감춘다 |
| **생성 XLSX 덮어쓰기** | **덮어쓰지 않는다.** 같은 이름이 있으면 `… (2).xlsx` 로 비켜 만들고 실제 자리를 알려 준다 |

### 이번에 찾은 진짜 결함 — 한글 프로세스가 샜다

점검 중에 이 PC 에 **보이지 않는 `Hwp.exe` 가 17개** 떠 있는 것을 발견했다.
오후 4시 33분부터 시험을 돌릴 때마다 하나씩 쌓인 것이었다.

**까닭**: `hangul_available()` 이 "한글이 깔렸는가" 를 보려고 **실제로 한글 객체를 만들고**
끝내지 않았다. 이 검사는 견적서 화면이 열릴 때마다 돈다.

**고침**

1. `hangul_available()` 은 이제 **한글을 띄우지 않는다.** 등록부에서 ProgID 만 찾아본다
   (`com::prog_id_installed`).
2. 실제 변환은 `HwpApp` 이라는 껍데기가 들고 있다가 **버려질 때 반드시 닫는다.**
   중간에 오류가 나거나 되감기로 빠져나가도 `Drop` 이 돌기 때문에 남지 않는다.
3. `hangul_leaves_no_process_behind` 시험이 못 박는다 — 설치 검사 5번, 변환 2번, 실패 1번을
   해도 `Hwp.exe` 개수가 시작 때와 같아야 한다.

**얼마나 나빴나**: 쌓인 프로세스 탓에 전체 흐름 시험이 **153초**나 걸렸고 한 번은 아예 멈췄다.
치우고 고친 뒤에는 같은 시험이 **13.8초**에 끝난다.

> 남아 있던 프로세스는 창이 하나도 없는 자동화 찌꺼기였다(`MainWindowHandle = 0`).
> **프로그램은 남의 한글을 절대 강제 종료하지 않는다.** 사용자가 열어 둔 문서를 잃을 수 있기 때문이다.

## 6. P4-6 로그 정책

**지금 이 프로그램은 로그 파일을 하나도 쓰지 않는다.** `log` 만 쓰고 받는 쪽(logger)을 붙이지 않았다.

로그에 남기는 것은 다섯 줄뿐이고 모두 "무슨 일이 있었는지" 다.

```
마이그레이션 적용: 002_quote_source
자료 파일 준비 완료 (스키마 v2)
남아 있던 임시 파일 3개를 치웠습니다
PDF 글자 조각 0개 — 스캔본으로 본다
PDF 글자 추출 중 문제: <라이브러리 오류>
```

정책은 `src/logpolicy.rs` 에 적고 **시험이 코드를 직접 훑어** 지킨다.

| 시험 | 무엇을 막나 |
|---|---|
| `logs_never_carry_business_data` | 로그 인자에 품명·상호·금액·파일 경로·OCR 원문이 들어가면 실패 |
| `no_debug_printing_in_product_code` | 제품 코드의 `println!`·`dbg!` |
| `nothing_writes_a_log_file` | 로그 파일을 쓰는 라이브러리가 몰래 들어오는 것 |

화면(TypeScript) 쪽에도 `console.*` 이 하나도 없다.
자세한 오류 원인은 `AppError::detail` 로 **화면 쪽에만** 가고 파일로 쓰이지 않으며, 화면에는 `message` 만 보여 준다.

### 실제 샘플 End-to-End (`p4_full_end_to_end`)

**네 가지 형식을 한 작업에** 넣고 끝까지 간 뒤, DB 를 닫았다 다시 열어 이어지는지 본다.

| 단계 | 확인한 것 |
|---|---|
| 등록 | 바둑 XLSX · 로봇과학 HWP · 주산암산 JPG · 한자급수 PDF — 넷 다 파일명으로 자동 매칭 |
| 읽은 경로 | `structured` · `structured` · `ocr` · `pdf_text` 가 제대로 기록된다 |
| 값 | 444,000 / 900,000 / 68,000 — 형식이 달라도 같은 규칙으로 나온다 |
| 문구 | `바둑부 바둑교재(상상바둑) 1종` · `주산암산부 방과후 기초Yap! 상 외 3종` |
| 신뢰 | 사진은 `확인 필요` |
| 정산자료 | 별칭 여럿(토탈공예미니어처 1·2)이 한 부서로 합산된다 |
| 배분 | 거래처 하나인 부서는 자동, 가로 검증 일치 |
| 검증 | 빨강 15건 (견적서가 없는 부서들) |
| 생성 잠금 | 빨강이 있으면 `GENERATE_BLOCKED` 로 막힌다 |
| 확인 사유 | 사유를 적으면 풀린다 |
| 생성 | 재원 4개 파일 생성 · 되읽어 검증 통과 |
| **이어하기** | DB 를 닫았다 열어도 작업·견적서 4장·사진에서 읽은 품목 4건·확인 사유·만든 파일이 그대로 |

그 밖에 따로 고정해 둔 것: 거래처가 여럿인 부서는 **자동 배분하지 않고 막는다**
(`two_vendors_require_manual_allocation`), 0원 재원은 파일을 만들지 않는다(`e2e_baduk_full_flow`),
읽지 못한 견적서도 등록은 남고 직접 입력으로 이어진다(`unreadable_quote_does_not_block_the_work`).

| 생성 XLSX 실제 에듀파인 업로드 | **통과** |
| **원본 보기** | **문제 발견** — "불러오는 중…" 에서 내려오지 않음 → 아래 9장에서 고쳤다 |
| 복합기 스캔 PDF | 시험할 샘플이 없어 못 함 (아래 제한사항) |
| 여러 이미지 한꺼번에 | 직접 시험 못 함 (아래 제한사항) |

### 배포를 막지 않는 제한사항 (사용자 판단)

- **복합기 스캔 PDF 실사용 시험 미실시.** 실제 업무에서 스캔본을 쓸 가능성이 낮다.
  자동 시험(`jusan_scan_pdf_real`)으로 경로 자체는 확인돼 있다.
- **여러 이미지 대량 처리 실사용 시험 미실시.** 실제 업무는 보통 한 번에 1~2개 부서다.
  진행 상태 알림과 자동 시험 결과를 그대로 둔다.

## 9. 원본 보기가 "불러오는 중" 에서 멈추던 문제 (2026-09-13 수정)

### 원인 — React 훅의 의존성이 자기 답을 버렸다

불러오기를 `useEffect` 안에서 했고, 그 effect 의 의존성에 **자기가 켜는 `불러오는 중` 상태**가 들어 있었다.

```
누름 → effect 실행 → setPreviewing(true) → 다시 그림
     → 의존성이 바뀌었으므로 앞 effect 의 정리(cleanup)가 돈다 → alive = false
     → 새 effect 는 "이미 불러오는 중" 가드에 걸려 그냥 돌아간다
     → 먼저 날아간 요청의 답이 도착 → alive 가 false 라 **버려진다**
     → 상태는 영원히 `불러오는 중`
```

**언제나 이렇게 된다.** 사진이든 스캔 PDF 든, 크든 작든 똑같이 걸린다.
오류가 나도 같은 자리에서 버려지므로 오류 표시조차 뜨지 않았다.

Rust 쪽은 멀쩡했다. 실제로 재 보니(**릴리스 빌드**) 사진 17ms, 스캔 PDF 17ms,
4000×3000 큰 사진도 101ms 였다. IPC 로 보내는 양도 사진 한 장에 130KB 다.

### 고친 방법

1. **불러오기를 effect 에서 꺼냈다.** 이제 `useSourcePreview` 훅의 보통 함수이고 **누를 때만** 부른다.
2. **요청 번호**로 늦게 온 옛 답을 가린다. 빠르게 여러 번 누르거나 다른 견적서로 옮겨도
   화면에 엉뚱한 원본이 끼어들지 않는다.
3. **시간 제한 20초.** 넘으면 실패로 보고 안내한다. (원래 일을 멈추지는 못하지만 화면은 기다리지 않는다.)
4. 상태를 네 가지로 좁혔다 — `idle` · `loading` · `ready` · `failed`.
   **`loading` 은 반드시 `ready` 나 `failed` 로 끝난다.** 그 사이에 갇히는 자리가 없다.
5. 큰 사진은 `thumbnail`(상자 평균)로 줄인다. 4000×3000 에서 `Triangle` 보다 두 배 이상 빠르고
   여러 픽셀을 평균 내므로 글자도 또렷하다.

### 화면은 반드시 셋 중 하나로 끝난다

| | 언제 | 화면 |
|---|---|---|
| **A** | 사진 · 스캔 PDF | 원본 그림 (쪽 딱지와 함께) |
| **B** | XLSX · HWP · 글자 PDF | 왜 그림이 없는지 + **원본 파일 열기** |
| **C** | 실패 · 시간 초과 | 빨간 글씨로 까닭 + **원본 파일 열기** + **다시 시도** |

### 전달 방식은 그대로 두었다 (base64)

"원본 전체를 거대한 base64 로 보내는 구조인가" 를 재 봤다. 아니었다.
화면용으로 **한 변 1600픽셀까지 줄인 JPEG** 를 보내므로 사진 한 장이 130KB(큰 사진도 447KB)다.
병목은 전달이 아니라 **그림 디코딩**이었고, 그것은 어느 방식을 써도 같다.

로컬 파일을 웹뷰가 직접 읽게 하는 방법(asset 규약)은 **쓰지 않았다.**
견적서는 사용자가 아무 폴더에서나 고르므로, 그 길을 열려면 파일 접근 범위를 넓혀야 한다.
**보안을 넓히면서 얻을 속도가 없다**(이미 17ms 다).

### 성능 — OCR 을 다시 돌리지 않는다

스캔 PDF 원본 보기는 P3 이 쓰는 **쪽 그림 꺼내기만** 다시 한다. 글자 인식은 하지 않는다.
시험이 이를 시간으로 못 박는다: OCR 은 한 장에 6초가 넘는데 원본 보기는 **3초 안에** 끝나야 통과한다
(실측 248ms, 릴리스 17ms).

### 덤으로 찾은 것 — 한글이 `%TEMP%` 바깥에 저장하면 멈춘다

이 문제를 고치며 회귀 시험을 돌리다 **한글이 19분째 매달려 있는** 것을 발견했다.

한글은 자기 작업 폴더 밖의 경로로 저장하려 하면 "파일 접근 승인" 을 물어본다.
그런데 우리는 창을 감춰 두고 자동화하므로 **그 물음이 보이지 않는다.** 그대로 영영 기다린다.
HWPX 변환은 처음부터 `%TEMP%` 안에서만 했기 때문에 멀쩡했고, P2 에서 더한 PDF 내보내기가 걸렸다.

**고침**: `save_as` 는 이제 언제나 `%TEMP%` 안에 만든 뒤 원하는 자리로 **옮긴다.**
시험 `save_as_outside_temp_does_not_hang` 이 바깥 폴더로 내보내 **1분 안에** 끝나는지,
중간 파일이 남지 않는지 본다(실측 1.8초).

### 시험

| 어디서 | 무엇 |
|---|---|
| Rust | 실제 주산암산 JPG · 스캔 PDF · 글자 PDF · XLSX · 없는 파일 (`preview_of_real_samples`) |
| Rust | 깨진 그림 · 큰 사진(줄이기와 시간) · 같은 파일 반복 호출 |
| TS (`check-preview`) | 상태 넷의 화면 문구, "갇히는 자리 없음", 시간 제한 동작 |
| 브라우저 (`test/ui/preview.html`) | **제품과 같은 훅**으로 느림·멈춤·오류·그림 없음·연타 8회·견적서 이동 |
| Rust | 한글이 TEMP 바깥으로 내보낼 때 멈추지 않는가 (`save_as_outside_temp_does_not_hang`) |

브라우저 확인에서 `loading` 에 갇힌 경우는 **한 번도 없었다.**
불러오는 중에 다른 견적서로 옮기면 접히고 `idle` 로 돌아가며, 늦게 온 옛 답은 화면에 끼어들지 않았다.
